# 固定 IPv6 直连与 YouTube 下载节奏

此方案让 yt-dlp 直接连接 YouTube / Google 视频 CDN。没有第三方解析渠道，也不会轮换地址来继续请求已触发验证的站点。IPv6 必须已配置在 Docker 引擎所在宿主机上，并具备正常路由。

## 网络与部署

使用当前 Docker context（支持 Windows 上的 Docker SSH context）创建专用 IPv6 网络：

```powershell
.venv\Scripts\python.exe scripts/setup_ipv6_network.py --source 2a06:f901:c001:100::fdb0:a5a2
docker compose -f compose.local-mysql.yaml -f compose.ipv6.yaml -p youtube-downloader-local up -d --build
```

`--source` 必须填写你自己的宿主机已配置公网 IPv6。上面的地址仅属于此次美国服务器。脚本不会覆盖已有的不匹配网络。若 Docker 可执行文件不在 PATH，可追加 `--docker "C:\Program Files\Docker\Docker\resources\bin\docker.exe"`。

专用网络使用私有 IPv6 子网 `fd42:76b7:2026::/64`，Docker 的 `com.docker.network.host_ipv6` 将它的出站流量 SNAT 到指定公网 IPv6。原有默认网络、MySQL 内部连接和端口映射继续保留。当前已在 Docker Engine 29.9.2 上验证；旧版本需先确认支持该选项。应通过实际出口检查确认效果，不能只看地址是否出现在网卡上。

网络是 external 类型，不随 Compose down 删除。**以后部署仍需追加 `-f compose.ipv6.yaml`**；仅使用原 Compose 文件重建容器会失去额外 IPv6 网络，而配置中的 `::` 仍要求 IPv6，导致连接失败。

在页面“登录与网络”中设置直连源地址为 `::`，并在“网络与代理”中选择直连。`::` 表示只使用 IPv6；具体公网地址由上述 Docker SNAT 决定，不表示随机轮换这台服务器的 16 个地址。

## 下载策略

| 设置 | 本次初始值 | 含义 |
|---|---:|---|
| 下载方式 | yt-dlp | 直接访问源站 |
| 视频启动最小间隔 | 5 秒 | 本实例所有下载进程共享，传输可并行 |
| 传输上限 | 4 | 自动调节的上限，实际占用可能更低 |
| 解析上限 | 1 | 避免大量视频同时请求元数据 |
| 分片并发 | 2 | 非分片 HTTPS 下载不一定受它影响 |
| 本地 / 共享连接预算 | 8 / 8 | 不把工作进程数等同于连接数 |
| 429 最短冷却 | 300 秒 | Retry-After 更长时服从更长时间 |
| 匿名重试 | 关闭 | 不为通用 Video unavailable 再增加一次匿名解析 |

登录预检和 yt-dlp 会绑定相同的直连源地址；预检缓存也按源地址隔离。此设置不强制浏览器的地址族，因此使用浏览器人工登录时仍须另行核对实际出口。

视频启动间隔不等于每个 HTTP 请求的间隔，更不是 YouTube 公布的安全配额。登录检查通常缓存 5 分钟；下载期间每次使用临时 Cookie 副本，避免下载器覆盖上传文件。Cookie 文件中的过期时间尚未到，也不代表服务端仍认可登录。

## 限制与恢复

- 验证码、机器人验证和确定的登录失效仍暂停实例，保留任务；不会自动切换其余 IPv6 继续冲请求。
- 429 触发共享范围冷却，恢复后沿用单路观察；没有 Retry-After 时也至少等待配置的最短时间。503 不自动等同于限流。
- 私有、删除、地区和权限问题按具体视频处理，不因单个视频不可用判定整个出口故障。
- 若显式开启匿名重试，其机器人验证会标明 `anonymous_fallback`，不会直接宣称上传 Cookie 已失效；暂停保护仍保留。
- 本地渠道繁忙会同时延迟工作进程再次领取，避免大队列不停领取和释放无关任务。等待期间不持有数据库事务或任务租约。
- 临时文件预算和物理剩余空间是两个独立限制；大视频与合并副本均需空间。不能用增加工作进程掩盖预算不足。

16 个同网段 IPv6 不等于 16 份独立站点额度，也不增加网卡带宽。保持有效登录、稳定出口和可控请求节奏比盲目增加地址数量更重要。任何短期测试都不能保证长期不触发源站风控。
