**2. “格式不可用”已有更具体的前置原因**

在详细样本的 15 个格式失败中，11 个任务日志仍存在，4 个已经清理。11 个现存日志全部在最终 `Requested format is not available` 之前明确出现：

```text
This video is drm protected and only images are available for download.
```

这些任务在提取信息阶段失败，没有进入媒体传输。当前配置未指定固定格式 ID，使用默认 `bestvideo*+bestaudio/best`；不是人为锁定某个不存在的清晰度编号。

具体含义是：**下载器在当次会话里最终只获得图片格式，没有可用音视频格式。**它并不能证明该视频在所有账号、所有合法客户端条件下永久不可下载。一个样本还同时出现年龄验证要求、部分客户端缺少媒体 URL 和 SABR 提示，应保留这些上下文。

对照样本中的正常任务也会出现“某个客户端的 DRM 格式已跳过”警告，随后仍能选中音视频并成功下载。仅凭跳过警告不应判定整条视频不可下载；“最终仅剩图片”才是本批失败更直接的证据。

服务器 yt-dlp 版本为 `2026.10.26`，Node 存在，日志明确记录使用 Node 处理 JS challenge；现存失败日志未发现 `challenge solving failed`。这不能证明所有 JS 求解都正常，但缺少证据将本批失败归为“未安装 JS 运行时”。

后续可改进：页面在泛化的“格式不可用”之外展示当次“仅获得图片格式”以及年龄验证等已有证据。处理此类内容问题应保留合法访问和媒体完整性要求，不能以降低画质或增加重试次数保证解决。本轮没有尝试绕过 DRM 或验证。

**3. 两次 HTTP 403 都集中在一个 Cookie**

异常账号使用匿名标识 `8fec61fe…`，没有在本文记录账号名称或凭据。

| 项目 | 实测 |
|---|---|
| 异常账号完成任务 | 2 次失败，均为 HTTP 403；该窗口无成功任务 |
| 其他 11 个账号 | 每个均有成功任务，合计 403 次成功 |
| 两次失败完成时间 | 21:06:04、22:06:35 |
| 第二次失败 | 已选中 `399+251`、1080p / 50fps，开始获取媒体数据时返回 HTTP 403 |
| 已保存恢复策略 | `repeated_http_403`，账号级冷却，恢复模式，单路恢复额度 |
| 当前冷却截止时间 | 23:06:35；这是 22:22 快照，后续新结果可能改变 |

第二次失败距离第一次约 1 小时，符合已保存的冷却后低频恢复过程。状态中的 `denied_cooldowns=3` 是退避档位上限，不等于只有 3 次历史失败；本轮事件与先前决策快照存在更多早期 403 记录。

目前证据支持优先检查该账号会话及其媒体请求条件。其他账号在同一出口成功，当前不能将问题直接说成整个出口 IP 被封。403 本身也不能确认 Cloudflare 或验证码。

该账号通过过登录检查不代表媒体访问一定成功：登录预检和 CDN 媒体传输是不同请求。更换账号对照、更新该 Cookie 或停用它会改变运行策略，本轮没有执行。

诊断还有一个显示细节：第二次 403 的结构化证据已正确记录 `phase=transfer`，而进度末状态仍为 `waiting_request`，因为在收到首批媒体字节前没有进入下载进度钩子。排查失败位置应优先使用结构化阶段；后续可细分“保护间隔等待”和“媒体请求等待响应”。

**4. 已修复：响应提前中断被误当成永久失败**

实际失败任务 `605188c3…` 于 21:41:15 结束。关键错误为：

```text
[download] Got error: 215403 bytes read, 9758503 more expected.
Giving up after 2 retries
```

这是响应未读完整。`215403` 是字节数，不是 HTTP 403；实际结构化状态码也为空。下载器内部的两次传输重试已经耗尽，但应用层仍有独立的任务尝试上限。原分类器将被包装成字符串的此类错误识别为 `unknown / retryable=false`，导致本次尝试后直接失败。

本地修改 [download_policy.py](../webapp/download_policy.py)：

- 识别标准库和 yt-dlp 的 `IncompleteRead` 异常，亦识别下载器包装后的严格字节计数信息。
- 归类为 `transient_failure`，沿用现有至少 60 秒冷却和任务尝试次数上限。
- 403、429、验证要求、内容限制和本地资源异常仍按已有分类优先处理。

没有修改并发、传输分块、Cookie、账号保护、源站请求间隔或最大尝试次数。应用层重新尝试可能需要重新下载部分文件，不能据此承诺断点续传或保证成功。

验证覆盖真实错误经 `DownloadFailure` 包装后的路径、保留类型的异常、状态码与内容限制优先级，以及 worker 处理后进入延迟队列、达到次数上限后结束。全部测试使用本地临时状态和模拟执行，没有向 YouTube 发请求。

```text
py -3 -m unittest tests.test_download_policy tests.test_diagnostics tests.test_cookie_pool tests.test_channel_scheduler tests.test_downloads
Ran 91 tests — OK
```

测试位置：[分类回归](../tests/test_download_policy.py)、[任务重试与次数上限回归](../tests/test_diagnostics.py)。修复尚未进入生产镜像；服务器后续同类错误仍会保持原行为，直到部署。

**5. Compose 冲突的具体线索**

重新读取实际容器 ID、创建时间和 Compose 标签，避免按容器名字推断新旧：

| 容器实际 ID | 名字 | 创建时间，北京时间 | 现状 |
|---|---|---|---|
| `46e34e10ebd3` | `youtube-downloader-local-mysql-1` | 09:09:51 | 已授权停止的异常容器 |
| `f936e15232d6` | `46e34e10ebd3_youtube-downloader-local-mysql-1` | 14:12:11 | 健康的替换容器 |
| `dd3cabe05920` | `youtube-downloader-local-redis-1` | 12:56:31 | 健康 |

两个 MySQL 的 Compose 配置哈希不同，项目和服务相同、数据卷相同；健康容器还有 `com.docker.compose.replace=mysql-1` 标签。与创建时间结合，符合替换后遗留容器没有彻底整理的情形，但现有 Docker 事件仅返回最近 256 条，大量为健康检查，不足以还原最初操作顺序。

此前把异常容器称为“新容器”不准确，已同步修正上一份报告。已停止的目标始终是实际 ID `46e34e10ebd3`，健康容器与数据保留情况没有变化。

Redis 的标签仅有项目、服务和实例号，缺少正常 Compose 容器常见的 `config-hash`、`oneoff`、`version` 等身份信息。它的实际 ID 与用户最初贴出的 Redis 名称冲突报错完全一致。这是“同名容器存在，但部署工具无法按完整管理身份处理”的直接排查线索；未执行重建来复现冲突，也不能只靠缺失标签确定当初是谁创建了它。

部署来源也不一致：

- MySQL 的标签记录 `D:\ProgramData\auto-video-download-and-upload`，Compose 版本标签 2.40.3。
- 应用的标签记录 `D:\pydaima\auto-video-download-and-upload`，Compose 版本标签 5.1.0。
- 两者使用同一个项目名 `youtube-downloader-local`。目录变化没有隔离同名项目，容易让不同配置轮流管理同一组资源。
- Linux 服务器当前没有可用的 `docker compose` 子命令；部署记录来自 Windows 客户端。标签中的 Windows 路径不在服务器上是预期情况，不能据此说项目文件丢失。
- 本地默认 Docker 上下文为 `desktop-linux`，另有一个已保存的 SSH 上下文。裸命令未明确指定上下文时，不能保证指向本次检查的服务器；已有 SSH 上下文的别名与目标 IP 本轮未确认一致。

维护时应先统一部署目录、项目名和 Docker 目标，保留数据卷并确认健康依赖后再整理容器。只更新应用时使用 `--no-deps app` 可避免顺带处理依赖；仅此参数不会修复既有管理标签和遗留容器问题。
