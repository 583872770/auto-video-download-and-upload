# 高并发与长时间运行检查（2026-11-06）

本轮接续[失败追查](failure-investigation-20261106-evening.md)，重点检查任务并发、租约、连接池、资源积累和异常恢复。生产侧仅读取；复现、并发回放和代码修复均在本地，**修复尚未部署**。

## 优先处理的风险

| 优先级 | 问题 | 触发条件与后果 | 证据与处理状态 |
|---|---|---|---|
| 高 | Cookie 池容量越过本机内存及数据库工作进程预算 | 扩大账号池或提高每账号并发后，进程数直接增长；可能引发连接等待、内存不足、心跳超时与恢复重试 | 本地确定性复现；尚未修改容量策略 |
| 高 | 正常结束与心跳续租存在竞态 | 正常提交成功、失败或释放任务，恰好遇到心跳更新，被误判成任务归属丢失，进程强制退出并重建 | 生产已有 3 次；本地已修复并增加回归测试 |
| 中 | 主数据库连接池配置不生效，预算算法不一致 | 按环境变量缩小连接池没有实际效果；并发扩大后连接总量与配置预期不符 | 生产配置、实际计算和本地对照一致；尚未修改 |
| 中 | 字幕工作进程临时目录漏清理 | 字幕进程崩溃或被终止后，遗留缓存可逐渐占满缓存预算，形成磁盘等待 | 本地复现并修复；生产采样时该目录没有遗留文件 |
| 较低 | 工作进程历史表缺少心跳索引及保留策略 | 频繁重启后历史记录增长，查询在线进程每次扫描、排序历史行 | 生产 EXPLAIN 确认；当前仅 451 行，尚非瓶颈 |

## 1. Cookie 容量需要再经过本机资源准入

`webapp/throughput.py` 已计算内存容量和 `VIDEO_WORKER_DB_CONNECTION_BUDGET`，但 Cookie 池分支随后将上限覆盖为账号容量；`runtime_limits()` 也直接使用账号容量。普通模式的自动压力调节在 Cookie 池模式中不启用。

本地使用以下固定输入：总内存 512 MiB、可用 64 MiB、CPU 99%、工作进程数据库预算 48、每进程连接池 2、账号池容量 64。结果依然为 **64 个工作进程、64 路传输**。这是调度决策复现，没有启动 64 个真实下载。

生产目前每个 Python 下载进程 RSS 大致 130–175 MiB。仅按这个量级估算，64 个下载进程约需 8–11 GiB，尚未包括 MySQL、主服务、FFmpeg、Node、浏览器和传输缓冲。实际占用依下载方式、分块数及任务阶段改变，不能用该估算承诺容量。

连接上限也存在相同问题：64 个下载进程 × 2，加维护、字幕各 2，再加主服务最多 16，配置潜在总量约 **148**；MySQL 当前 `max_connections=151`，留给其他访问的余量很少。连接池按需开连接，因此 148 是潜在上限，**不是已观测到的占用**。

建议保留账号池自己的限速、冷却和账号容量逻辑，同时增加本机硬上限：实际可运行数量取账号容量、进程连接预算、内存容量的较小值；额度不足的任务留在队列，不计失败。需要同时统一控制器、`runtime_limits()`、进程启动和页面显示。现有测试明确要求账号池独立于普通模式的 worker_count 和压力调节，本轮没有直接改变这一既有产品行为。

## 2. 实际发生的结束 / 心跳竞态

生产日志中三次 `heartbeat_ownership_lost` 与该任务正常提交结果发生在同一时间：

| 时间（北京时间） | 任务匿名标识 | 已提交状态 | 随后行为 |
|---|---|---|---|
| 22:25:36 | `97b7ce72…` | 失败，第 3/3 次，远端断开连接 | 槽位 15 退出码 2，随后重建 |
| 22:44:48 | `dc694102…` | 成功，第 1 次 | 槽位 15 退出码 2，随后重建 |
| 23:00:25 | `5f7805f0…` | 成功，第 1 次 | 槽位 11 退出码 2，随后重建 |

原执行顺序是：主线程提交 `finish/release`，数据库清除 worker_id / running 状态；心跳线程此时更新不到任务，立即强制退出进程；停止心跳的信号原本要到后面的 finally 才设置。

两条成功记录都已保存，没有证据表明这三次造成重复下载。已确认的影响是多余进程重建、误导性租约告警，以及强制退出跳过部分收尾的风险；高吞吐、长时间运行会增加碰到该窗口的机会。

本地增加 `webapp/lease_guard.py`，以同一把锁协调续租与结束 / 释放操作，在正常提交返回后立即发布停止信号。成功、失败、退避释放路径均已接入。提交抛出异常时继续保留续租；真正被其他工作进程接管时依然报告归属丢失。原有 watchdog 的超时退出机制继续生效。

新回归测试用真实本地任务库将线程停在“数据库已提交、结束调用尚未返回”的窗口，确认旧的直接续租会返回 False，而修复后的并发续租会正常停止；另验证真实归属丢失及数据库提交异常。

## 3. 环境变量与实际连接池不一致

生产环境配置 `VIDEO_DB_POOL_SIZE=5`、`VIDEO_DB_MAX_OVERFLOW=2`，但 `calculate_pool_size()` 返回 `(9, 7)`。本地改为 `(2, 0)` 后，计算结果仍为 `(9, 7)`。

原因是主服务计算器没有读取这两个变量，而是使用另一组预算，默认假定 16 个工作进程、每个 2 个连接，再分配剩余额度。实际账号容量变化不会更新该假设；吞吐控制器使用的则是 `VIDEO_WORKER_DB_CONNECTION_BUDGET`。此外，工作进程的 overflow 在计算器中固定为 0，吞吐预算算法却读取该变量。

建议统一一套明确的总预算：主服务保留量、下载进程、字幕 / 维护进程及运维余量全部纳入；显式连接池配置必须生效，页面展示实际值。单纯调大 MySQL max_connections 不能解决进程及内存预算失配。

## 4. 长期积累与清理

`DiskBudget._clean_diagnostics()` 原先只识别数字槽位和 maintenance，漏掉 `worker-subtitles`。本地已加入字幕角色，测试确认：过期且无工作进程持锁的目录会清理，活动目录和近期目录会保留。

工作进程表的主键包含每次启动生成的身份；退出后旧行继续保留。在线查询为 `heartbeat > 当前时间 - 90秒 ORDER BY heartbeat DESC LIMIT 500`。生产目前精确 451 行，仅有主键索引，EXPLAIN 为 `ALL / Using where; Using filesort`。建议增加 heartbeat 索引，并为陈旧运行状态设保留期限；目前规模较小，不应当作当前性能下降的解释。

业务任务、去重预约、配置快照也需要容量规划。生产表统计：tasks 数据与索引约 708 MiB，去重预约约 104 MiB，快照约 26 MiB；information_schema 的行数是估算值。快照有内容哈希复用，不能说每个任务必定新增两条，但旧配置 / 会话版本未见回收流程。业务历史与去重信息不能随意删除，应设计归档及引用检查，再回收无引用快照。
