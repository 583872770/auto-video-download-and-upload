# 单实例 Cookie 账号池

只运行一个下载实例，Cookie 内容保存在数据库并按实例隔离，使用时生成本地缓存。下载前按会话取得数据库许可，任务直到完成都使用同一份 Cookie 和同一个实例出口。账号池只支持 yt-dlp，单次执行不换身份重试；任务释放回队列后可由其他健康账号执行。

## 调度规则

启用 Cookie 池时独立调度，忽略设置中的运行模式 `throughput_mode`、实例并发上限 `worker_count` 及自动调节带宽目标，不进行自动并发增减。每约 5 秒读取会话容量，工作进程与传输目标按池容量更新。关闭池后恢复使用原有运行模式与并发上限。渠道选择策略 `scheduler_mode` 独立生效，渠道、解析和连接预算继续限制实际准入。

诊断页将 Cookie 文件数、核心会话数、登录检查与账号身份分开显示。相同核心凭据合并，不同核心凭据也不代表不同 Google 账号，当前没有核验真实账号身份。启动窗口是本地调度估算，不保证源站可用。

- 「Cookie 与登录 → 会话并发、出口与请求节奏（高级）」可设置 `youtube_cookie_session_limit`，范围 1～64，默认 2。连续成功至少 5 次、从首次成功起经过至少 10 分钟完成预热，预热前每会话 1 个任务，预热后使用设置上限。
- 总池容量为未冷却核心会话的当前容量之和，执行器最多承接 64 个任务。无可用会话、池被拦截或处于冷却时仍停止准入；容量为 0 时保留一个检查进程，但池许可不会放行下载。降低上限不强制中断已有任务，超出新值时等待任务释放。修改实例运行模式和并发上限不会改变池的会话许可、进程数或传输目标。
- 每账号初始启动间隔至少 60 秒，另加 2～10 秒间隔扰动。稳定后逐步降至 45 / 30 秒；整个实例启动间隔为 `max(10, 30 / 核心会话数)` 秒。因此总并发上限不会让任务立即同时启动。
- 按 SID / PSID 等核心会话凭据合并额度；辅助字段 LOGIN_INFO 等发生变化，也不能把相同核心会话算成多个账号。页面会标出合并额度的文件。不同核心会话仍不能证明账号不同，也不能证明拥有独立额度。
- 可识别的临时网络错误重置该会话预热状态，启动间隔加倍，最高 600 秒，并冷却至少 60 秒。其他健康会话保持各自容量，不增加容量补偿冷却的会话。
- 明确账号限流仅冷却该核心账号至少一小时；HTTP 429 仅冷却该账号，默认 300 秒，均遵守更长的 Retry-After。其他健康账号保持原有容量继续；所有账号冷却时自动等待最早到期账号，不暂停实例。冷却中不发新下载、字幕或登录检测请求。到期先单任务、至少 180 秒间隔；连续成功 3 次且观察满 10 分钟后降至至少 120 秒；连续成功 5 次且观察满 30 分钟后恢复设置并发，间隔仍至少 120 秒。配置间隔更高时服从更高值。再次限流重新冷却，临时故障重置连续成功观察。登录失效、额外验证及旧版本人工停止仍需手动处理，不因升级解除。
- 私有、删除、已明确的内容限制和格式不可用单独记录，不据此惩罚其他账号。未知错误不能作为提高并发的依据。
- 数据库许可绑定任务所有者和租约，进程失效后旧许可不继续占用；多个进程共用账号上限。源站、解析和出口相关的共享限制保持生效。

## 配置与页面

在实例配置文件增加已保存的 Cookie ID 列表：

```yaml
download_methods: [yt_dlp]
youtube_cookie: Cookies/profiles/<第一份 Cookie ID>.txt
youtube_cookie_pool:
  - <第一份 Cookie ID>
  - <第二份 Cookie ID>
  - <第三份 Cookie ID>
youtube_start_interval: 60
youtube_cookie_session_limit: 2
youtube_sleep_preset: true
youtube_cookie_fallback: false
fragment_concurrency: 1
```

开启前停止实例、等待当前下载结束，逐份检测登录。`youtube_cookie` 也需指向池中一份有效文件，供现有启动检查使用。每会话任务上限可在页面保存，作用于后续领取任务。例如两个未冷却核心会话、会话设置值 3 时，预热前总容量 2，全部预热后总容量 6；无论实例并发设为 1 还是 20，运行模式选择自动还是自定义，池容量都相同。若两份文件属于同一核心会话，则合并为一个会话，预热前 1、预热后 3。

「Cookie 账号管理」会标出账号池成员。池中的文件禁止直接删除。停止实例后点击「使用此 Cookie」会关闭账号池，切回单 Cookie；限流和冷却不会因此清除。

账号冷却、恢复观察和人工拦截均保存在数据库，重启不会清除。自动冷却不需要解除拦截；以下人工操作只适用于登录验证及历史停止状态。停止实例并等待全部任务结束后，在账号管理中点击「检查全部账号并解除拦截」；只有全部在线检查通过、账号冷却已结束且没有活动任务时才解除拦截，之后仍需手动恢复下载。源站共享冷却不会清除。每行同时显示该会话的设置上限、实际生效上限、启动间隔和冷却剩余时间。

关闭再启用 Cookie 池也会沿用原停止状态。任务在池准入时被旧状态拒绝，尚未选择 Cookie 或发起视频下载请求；这不能作为本次 YouTube 限流的证据。列表和错误会显示原停止时间；新事件区分明确账号限流、HTTP 429 和登录检查/额外验证，旧记录没有具体原因时标为未知。风险诊断将历史池拦截单独展示，不再把通用「账号池检测到限流或登录验证」认定为明确账号限流。

工作台「并发与等待」增加「等待与恢复依据」及最近触发事件。同一次失败跨渠道、请求节奏、会话和池使用同一个事件编号，展示发生阶段、HTTP 证据、错误摘要、影响范围及截止时间；冷却取较晚截止时间，不把各层时长相加。旧任务的成功不会提前清除较新故障的冷却。完整规则见 [下载错误与恢复决策](download-recovery-decisions.md)。

使用 `youtube_source_address: '::'` 时，容器必须连接有 IPv6 出口的网络。Compose 重建请同时指定 IPv6 覆盖文件：

```sh
docker compose -f compose.local-mysql.yaml -f compose.ipv6.yaml up -d --build
```

不需要启动 `compose.account-b.yaml`。原第二个实例可以保持停止，保留其卷以便备份。

## Cookie 持久保存

Cookie 内容、名称和创建时间保存在同一个业务数据库的 `youtube_cookie_profiles` 表中，按实例标识隔离；未注册实例按配置目录隔离。首次访问管理列表或读取 Cookie 时会将旧的 `Cookies/profiles/*.txt`、同名 JSON 和 `Cookies/youtube.txt` 自动导入，保留原 ID、名称和账号池配置。数据库已有记录不会被残留文件覆盖。

上传名称可留空或只输入空格，默认使用上传文件名（含 `.txt` 扩展名），显式名称优先。名称上限 80 字，过长的文件名需手动填写短名称。

yt-dlp 需要文件输入，使用时会在原路径生成权限受限的缓存；缓存丢失后由数据库恢复。数据库是账号管理的唯一数据源，直接编辑缓存不会更新账号。旧 JSON 可保留用于回滚；删除账号会清除数据库中的 Cookie 内容并记录删除标记，避免残留文件重新导入。

重新部署需要保留数据库和原实例标识。跨服务器迁移要迁移数据库及实例配置；数据库和备份包含登录凭据，应限制访问。保存成功不代表登录有效，重新部署也不会解除登录失效、限流或冷却。
