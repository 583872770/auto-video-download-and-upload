# 洛杉矶下载工作台刷新停顿诊断

目标：216.227.169.90，2026-11-06 北京时间约12:17起采样。

## 结论

已经观察到严重、间歇性的 InnoDB 行锁争用和磁盘 I/O 压力。页面接口通常能快速返回，但下载进度写入、任务续租和调度可能排队数十秒，所以页面能够收到响应却显示相同的进度。这能够解释本次观察到的停顿；尚未通过用户浏览器录制排除其他网络或渲染因素。

主要问题是批量导入查重的宽范围加锁查询，与持有共享调度资源行锁的许可证清理事务互相影响；默认128MiB InnoDB缓存进一步放大磁盘访问成本。没有观察到元数据锁等待，不能将这一现象表述为数据库一直锁住整张表。

本次只读诊断，没有修改 MySQL 参数、应用代码或业务数据，没有暂停或重启容器。诊断使用正常认证的只读 HTTP GET；临时诊断会话仅存在进程内存，不记录签名密钥或会话凭据。

## 服务器与数据库证据

- 4 vCPU、约16GiB内存；可用内存约11GiB，系统盘193GiB、剩余约180GiB，无交换分区。
- 应用、MySQL容器均健康；一份容器快照显示应用约0.80核、MySQL约0.51核。

- MySQL 实际版本8.4.13；InnoDB buffer pool仅134217728字节，即128MiB。
- information_schema估算：tasks数据约267MiB、索引约441MiB，合计约708MiB；download_reservations约104MiB；task_snapshots约26MiB。行数为估算，非全表精确计数。
- 首轮15秒采样：InnoDB物理读取约24.9MB/s，逻辑读取未命中占约3.04%。此前启动以来累计物理读取已超过76GB。

- 导入仍在运行：一份快照显示1个未完成导入，已处理并加入约366000项；后续工作台排队量达到约373800项。

## 锁等待与慢 SQL

第一轮4次、间隔约5秒的采样中：

- Innodb_row_lock_current_waits始终为21。
- data_lock_waits中约211条等待关系，不能将其误读为211个独立等待进程。
- 最老事务持续约26–36秒。
- pending metadata locks均为0，Table_locks_waited为0。

performance_schema启动以来汇总：

| SQL 类别 | 次数 | 平均耗时 | 最大耗时 | 主要证据 |
|---|---:|---:|---:|---|
| 调度资源行的 INSERT ... ON DUPLICATE KEY UPDATE | 39388 | 294ms | 40.05s | 累计锁等待约11566秒，为并发会话之和 |
| 任务续租 UPDATE | 2208 | 828ms | 23.05s | 几乎全部耗时在等待锁 |
| 同时更新进度与标题 | 3056 | 434ms | 25.04s | 几乎全部耗时在等待锁 |
| 导入查重 SELECT ... FOR UPDATE | 361 | 4.74s | 18.83s | 累计扫描约6480万行 |
| 清理过期下载许可证的 DELETE + 子查询 | 1937 | 561ms | 40.78s | 历史汇总有19次错误，错误类型尚未单独核实 |

随后连续锁链采样观察到 download_resources 主键记录排他锁争用，以及 tasks 主键记录争用；部分调度资源等待者被正在执行许可证清理 DELETE 的事务阻塞。锁有释放、再次出现的周期，并非持续不恢复。

相关代码：

- webapp/store.py：insert_downloads 中按1000项查重，video_id IN (...) OR url IN (...)，并对完整任务行使用 FOR UPDATE。
- webapp/channel_scheduler.py：_admit 在持有调度资源行锁的事务中，使用 DELETE ... task_id NOT IN (SELECT id FROM tasks ...) 清理许可证。

执行计划验证（EXPLAIN，未执行加锁查询或 DELETE）：

- 使用当前库中的批次和一条实际记录构造1000项查重样本，其余项为不存在的诊断占位值。
- 合并OR条件时，优化器选择ix_tasks_dispatch，仅使用action部分，估算每次扫描约171166行。
- video_id条件单独查询，选择ix_tasks_video，估算扫描约1000行。
- url条件单独查询，选择ix_tasks_url_prefix，估算扫描约1000行。
- 许可证清理DELETE计划使用resource索引和tasks主键定位，故其主要问题是事务锁依赖；不能简单认定该DELETE自身必然全表扫描。

这些是执行计划和现场等待链证据，并不等于已经对修改后的实现做过生产压测。

在应用容器内请求实际运行服务，使用已有账户的内存诊断会话，仅执行GET。每轮并行请求3个页面轮询接口；共22轮，每个接口22个样本，全部HTTP200：

这些数值不包含用户到洛杉矶的公网延迟，也不包含浏览器绘制时间。

长采样的前3轮工作台请求均返回200，正在运行的24个任务的完整进度指纹连续相同；同期锁链采样存在16个调度资源等待事务及任务记录等待。锁释放后进度指纹恢复变化。它支持“后台写入被阻塞导致数据停滞”的判断，但不能证明用户感受到的每次停顿都由同一原因产生。

Docker stdout/stderr近15分钟未提供有效业务日志，不能据此判断不存在死锁、超时或应用异常。诊断记录未输出或保存Cookie内容、订阅凭据、数据库密码。

## 建议的处理顺序

1. 将InnoDB缓存由128MiB提高至2GiB作为初始值，并持久化到实际Docker部署配置；保留事务持久性设置。该调整应在变更后检查内存与I/O变化，不能代替代码优化。
2. 优化导入查重：拆分可用索引的查询，减少返回列，缩小加锁记录及事务范围；保留跨导入并发去重、已移除条目恢复和导入游标原子提交语义。
3. 优化调度许可证清理：减少共享资源行锁持有期间对任务表的锁依赖，统一事务锁顺序、限制清理范围；保留任务所有者、租约和额度一致性校验，不能直接删除锁或去掉租约检查。
4. 优化后在仍有批量导入及下载的条件下复测：进度/续租最大等待、活动行锁等待数量、每秒物理读、HTTP时延及进度是否连续更新。

此时直接增加下载并发可能增加共享行锁等待，不应作为主要解决方案。
