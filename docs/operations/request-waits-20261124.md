# 请求等待与平均带宽分析（2026-11-24）

本轮只读观察和代码核对，没有修改线上设置、业务代码或部署。目标是在保留账号保护的前提下，区分有意等待、额外开销与工作负载变化。

## 测量结论与边界

r67、r68 各自 600 秒窗口的宿主网卡接收均值为 571.98、467.16 Mbps，下降约 18.3%。但不是同一批视频的对照实验：成功任务数 100→109，文件数 690→851，成功产物字节 49.61→34.15 GB，失败数 66→1。每个成功任务的平均产物约 496→313 MB，每任务文件数 6.90→7.81。更小、更多的文件更容易被固定文件启动等待限制。不能据此断言 r68 传输实现降低了速度，也不能把全部下降归因于等待。

## 当前等待机制

| 层次 | 当前设置 | 作用位置 |
| --- | --- | --- |
| 账号任务启动 | 最低 50 秒，另加随机抖动；自适应保护可提高 | 同一个账号领取新视频任务 |
| 账号任务结束休息 | 10 秒 | 同一个账号结束网络获取之后 |
| 提取请求 | 0.75 秒 | yt-dlp 提取器请求之间，首个请求通常不等待 |
| 文件启动 | 随机 10～20 秒 | 每次封面、媒体轨道或单语言字幕文件下载前 |

账号单会话上限为 1，账号池全局启动间隔为 0，分片并发为 4。新任务最早开始时间由前次启动间隔、结束休息、账号冷却、预算等取最大值，不能简单相加为额外等待 60 秒。50 秒是配置下限，不代表所有账号实际都恰好 50 秒。

文件启动等待由 `youtube_sleep_preset` 启用。字幕从同一个 10～20 秒范围派生，不是额外叠加一份字幕专用等待。HLS 子分片不逐片再等 10～20 秒。前一个大文件已经传输了很久，下一文件仍会完整 sleep；当前实现不是按上次请求开始时间计算剩余间隔。

获取顺序是解析、视频信息本地写出、封面、媒体轨道、各语言字幕。媒体来源相同的轨道已有复用，不能假设视频和音频一定各下载一次。视频信息 JSON 本身不会多发一个下载请求。账号租约覆盖整个网络获取过程，包含文件等待；本地后处理才在释放账号后独立执行。

## 优化顺序

1. **字幕获取只做字幕工作。** 复用已解析轨道，避免每种语言创建新下载器并对完整视频信息再次执行 `process_ie_result`（包含格式处理与选择）；复用同一账号的会话、连接和 Cookie。保持每文件等待、单账号并发、大小限制、格式优选、回调和错误处理。该重复代码路径已确认，实际可节省多少 CPU/时间尚未单独测量，不应承诺必然满带宽。
2. **明确字幕语言范围。** 页面区分视频主语言、指定语言、全部来源原始语言，再独立选择人工优先/源自动备选。若用户只需要主语言，减少其他语言下载可以同时减少请求和账号占用；若仍要求全部语言，则必须保留全部。此项改变交付约定，需要用户选择，不能当纯性能修复静默实施。
3. **减少无效封面探测。** 区分来源明确给出的封面与上游推测地址，按画质/可靠性选取，缓存本任务已确认的 404/410，禁止额外 HEAD 探测。当前上游 `info.thumbnail` 来自原始封面列表，可作为可靠候选；直接优先它可能放弃未列出但实际存在的更高清图片，应提供清晰的最佳画质/减少探测取舍。不能跳过等待后紧密重试来声称风险不变。
4. **改准实时指标。** 区分文件启动等待、连接/首字节等待、真实传输、账号启动等待；当前 `waiting_request` 可持续到首个进度回调，`transfer_seconds` 也包含 sleep，不宜当作纯传输时间。使用 Redis 累计轻量指标，不添加高频 MySQL 进度写入。

不优先缩短 50 秒任务间隔，不提高单账号会话数，也不把数十种字幕并行发出。只调换封面/媒体顺序能改善首次看到视频下载的延迟，不能消除整轮等待；把 sleep 改成异步只能减少占用线程，不能凭空释放同一账号的保护配额。

后续若把“每文件额外 sleep”改成“按账号上次请求起点计算剩余等待”，长传输可抵扣间隔，但这确实可能提高单位时间的文件启动及新任务频率，不等价于现有策略，不能保证风控风险不变。应在上述低风险优化之后，另行设定请求频率上限，少量账号分组观察 403/429/账号限制和每账号请求量；不能与加并发、减任务间隔一起实施。
