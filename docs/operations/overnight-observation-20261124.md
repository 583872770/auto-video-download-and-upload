## 首要问题：播放器解算失败后显示为 DRM

北京时间 01:00～09:00 的完整 8 小时终态桶：成功测试任务 5127 个，失败 3261 个；失败原因 content_restriction 3032 个、drm_only 74 个、unknown 81 个、format_unavailable 40 个、private 18 个、deleted 11 个、access_denied 5 个。这些是任务终态计数，不能与请求异常次数相加。

09:39 抽查 3 个最新 content_restriction 任务，均出现以下顺序：

1. 获取 tv_samsung 与 web_embedded 客户端格式。
2. Node 执行新播放器 `b485e332` 的 challenge 时抛出 `TypeError: a.addOnDisposeCallback is not a function`。
3. yt-dlp 提示 `n challenge solving failed: Some formats may be missing`，部分 web_embedded 格式缺少 URL，并提示 SABR 可能性。
4. 最终抛出 `This video is DRM protected`，应用据最后异常归为内容限制，不可自动重试。

样本视频 ID：`E2G7tZ_LDMc`、`nyNC2sO_Roo`、`kCGxtk-qxfA`。这说明当前至少存在播放器 JavaScript 解算失败，不能把全部 DRM 结论当作真实内容加密。尚未在独立环境重现或升级对照，无法确定根因属于上游 solver、运行时还是本项目的播放器缓存包装。

优先验证播放器解算与缓存失效路径，再修正错误分类，避免前置解算失败被最终 DRM 异常遮住；修复后只重试确认受该故障影响的任务。不要据此绕过真实 DRM 限制。

## 账号节奏与请求等待

夜间小时统计记录 9 次账号限流事件（发生在解析阶段，源站明确提示 account rate-limited），6 次 HTTP 403，未记录 HTTP 429。约 09:34 有 33 个账号，3 个冷却、30 个可调度。403 请求次数不等同于最终失败任务数；账号限流也不一定返回 HTTP 429。

实时样本 27 个运行任务里，15 个在 waiting_request：8 个字幕、3 个封面、4 个视频；这是统一 sleep 预设的文件请求等待。当前代码对各个文件请求启动应用 10～20 秒等待，多语言字幕逐种请求会占用账号时间。账号调度上限 30 不代表同时有 30 个视频传输。不要以取消等待或强行加并发作为首选处理，因已有明确账号限流。

## 内存与 I/O 余量

系统可用内存从首轮约 4～5 GiB 下降到约 1.2～2 GiB。一次进程核对中，应用 Python 进程 PSS 合计约 8.76 GiB、USS 约 8.75 GiB，部分长时间复用的工作进程 RSS 约 320～354 MiB。RSS 合计不是可靠的独占内存指标，因此另核对 PSS/USS；这些值也不包含 MySQL 独立容器。

这说明应用常驻内存已占较多空间，可能压缩文件缓存并增加 I/O 压力，但尚不能据单次进程内存断言泄漏。应以跨任务对象释放、yt-dlp / 提取器生命周期和长期进程内存上限为下一项验证；在完成当前任务后回收进程，不能中断下载。

sysstat 时段磁盘平均读约 62 MiB/s、写约 184 MiB/s，iowait 峰值 16.4%。磁盘 I/O 是次要压力来源；没有证据表明 MySQL CPU 或 CPU steal 是当前主要瓶颈。Redis 约 2 MiB，无淘汰键或拒绝连接。
