# 后处理积压与低开销优化分析（2026-11-24）

## 结论

当前不能把后处理慢简单归因为 CPU 或两个处理槽位太少。两段独立约 30 秒的线上计数显示明显的磁盘等待；逐文件持久化、磁盘协调锁竞争、HLS 分片落盘和 MP4 二次整理，都与下载竞争同一块 VPS 虚拟磁盘。部分任务的“等待空间”实际上来自协调锁繁忙，需要与真实容量不足分开。

本轮仅运行有界只读诊断并分析代码，没有修改业务代码、配置、交付内容或部署版本。诊断没有额外请求来源站点、下载测试视频或运行磁盘压测。

上述结果表明当时有显著 I/O 压力，但不足以断言 VPS 磁盘的固定带宽上限或把原因归于其他租户。虚拟磁盘 busy 也不等同于物理设备性能极限。进程 I/O 计数可能包含已退出子进程，不能简单相加作为实际磁盘流量；短进程采样还会漏掉 FFmpeg 的一部分 CPU。

21:44 左右进一步核对：12 项本地任务的阶段为 `disk_wait`，具体原因全部为“本机磁盘协调繁忙，等待后自动重试”。这是 SQLite 协调超时，并不是这些任务各自又需要一份空间。全局容量受阻与局部协调锁等待同时存在，不能把 1275 条真实容量受阻记录全部说成误报。

## 代码中的开销和阻塞点

1. `webapp/delivery/processing.py` 在一个 `local_processing(..., 'delivery')` 槽位内遍历整个视频的全部产物。大量小字幕会占着与大文件相同的处理名额；队列领取按视频工作创建时间排序，没有考虑迅速释放多少字节。
2. 每个字幕格式不匹配时，`convert` 单独启动一次 FFmpeg。已有目标格式会直接交付，不能把所有字幕都描述成必经转换。
3. `publish` 在测试模式对每个产物重写完整 `.completed-files.json` 并执行 `fsync`；随后独立登记文件回执及相关业务计数。`completed` 又保存完整工作计划、遍历依赖并扫描工作目录以更新预留。随着字幕增多，列表和计划反复处理有累计开销。
4. 预算使用 SQLite 协调。原有预留校验已有只读快路径，不能说所有检查都写库；但进程启动/退出、文件边界、预留变更、扫描提交和维护修订仍争抢写事务。`DiskCoordinationBusy` 继承 `DiskPressure`，监控可能将协调超时变成中断重试和统一的空间等待阶段。
5. 获取阶段只有全部媒体和字幕请求结束后才将整份工作交给后处理；字幕失败时也会保存已取得的工作，但正常的长字幕等待仍将大媒体文件留在来源工作区。
6. 服务器 yt-dlp 2026.11.23 的原生分片实现先下载 `Frag` 文件，再读入并追加到总文件，flush 后删除分片、更新续传记录。项目 HLS 路径继承该行为。这是逻辑读写放大；页缓存可能合并写入，不能机械地说物理磁盘流量必然翻倍。
7. `convert` 和 `split_copy` 对 MP4 输出默认添加 `+faststart`，通常需要第二遍整理文件以把索引放前面。保留网页渐进播放需求时不能直接当无用功能删除。

## 建议的重构顺序

### 第一优先级：减少持久化和协调开销

- 同一视频的字幕按小批次转换，复用一个 FFmpeg 进程处理一批输入输出，保持现有格式、语言、字幕内容和网络节奏；逐文件验证和错误定位继续保留。原格式直交付仍使用原路径。
- 批量预取产物状态、登记回执和更新处理计划，避免每条字幕重复查全量状态、重写全量清单、执行独立同步提交。批次大小及时间必须有界，不能把整个大视频的交付做成一个长事务。
- 文件回执、业务计数和状态在批次内原子登记；只有持久化提交成功才能回收依赖。中断后按产物身份和已有文件恢复，防止重复统计或删除未登记成果。
- 预算只有申请、增额、收紧、交接和释放才变更；日常校验使用轻量只读状态。维护只核对发生变化的计划，不每轮对全部排队计划加锁和反复 stat。
- 协调繁忙独立显示、有限退避；只有已持有预留仍有效、无需增额且实际剩余空间安全时，才允许继续使用已有额度。仍不能申请未知的新额度，也不能因锁忙取消低水位保护。

这些变化首先降低事务、进程启动和小文件同步写次数，不依赖提高并发或加资源。

### 第二优先级：按文件依赖释放空间

- 快速测试且没有启用留样的任务，完成产物校验、回执提交及最后一个依赖后即可回收对应文件，不再等整视频的全部字幕处理完。留样及正式交付继续保留所需文件。
- 使用文件依赖与剩余引用计数，避免每次完成一个产物都从头遍历全部已完成输入。
- 轻量直接交付不长期占用重型媒体处理名额；优先完成能快速释放较多空间的工作，同时保留等待时长权重，防止大任务或字幕任务饥饿。
- 大文件完成后及时释放对应实际用量和预留；小字幕可按批次合并空间变更，不能降低真实占用检查的正确性。

### 第三优先级：文件完成即进入后处理

将整视频交接改为按依赖就绪交接：媒体下载完成后进入处理，网络继续按原节奏取字幕。获取与处理分别持有执行所有权；工作目录和文件必须分清写入者，不能让两个进程共用一个整体写锁后互相等待或误删文件。

这一项要配合前两项降低每份工作的成本。单纯更早排入同一个拥堵队列不会提高吞吐，甚至会扩大排队量。统一维护产物依赖和额度，不增加一套字幕专用并发、请求间隔或独立的空间预算。

### 后续：减少大文件写放大

- 对明确支持的普通点播 HLS 使用有界缓冲、按序写入，减少短命分片文件。保持现有请求数、重试、完整性、账号和冷却策略；复杂清单仍走完整支持路径。需要明确内存上界并计入现有预算，不能承诺零额外内存或把整视频装进内存。
- 核对素材预览和渐进播放对 faststart 的需要；离线交付可以避免不必要的第二遍移动，必须保留网页渐进播放的场景再选择合适的输出组织方式。不能未经确认改变客户播放体验。
- 保留媒体源和输出校验，复用同一不可变文件的探测结果；不靠省略校验或假登记测试产物提速。

## 观察和验收

实施时先记录一个稳定窗口，再分步验证；网络语言、请求间隔、账号并发及冷却保持不变。至少同时比较网卡接收、最终产出、后处理入队/完成速率、队列字节和最老等待时间，以及 CPU、I/O wait、写延迟、MySQL 写入和协调超时次数。仅看任务数量或瞬时下载速度不足以证明积压已解决。

不优先扩大 120 GiB 额度、清除有效预留、提高处理并发或设置新的固定下载限速。目标是用更少的落盘与提交完成同样的交付；若减少放大后输入仍长期超过 VPS 的磁盘处理能力，则仍需受控排队或更高 I/O 能力，软件不能保证在任意负载下同时无限接收且零积压。

- 静止计划以内容摘要和额度为标记，未变化时不再逐份加锁、访问远端任务并扫描文件；标记随额度删除而回收。后处理周转保护按处理名额保守覆盖缺额，不能把同一实际字节重复释放。
- 空间协调锁繁忙独立为调度等待，5 秒后可重试，不再伪装成容量不足等待 60 秒。真实容量不足仍按原保护逻辑等待。
- 原文件按未完成消费者引用计数回收；媒体先于字幕处理。未留样的完整快速测试，在登记及计划落盘后逐批回收产物；正式交付、留样和待补齐网络内容的文件继续保留。中途打开留样不发布缺文件的部分样本，提示下次完整测试生效。
