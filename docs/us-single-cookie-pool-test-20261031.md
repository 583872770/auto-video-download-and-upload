# 美国服务器单实例、三份 Cookie 测试

日期：2026-10-31（北京时间）。服务器：88.210.37.181。下载器：服务器内置 yt-dlp。使用已有任务，没有新增其他任务或第三方下载渠道。

## 结论

目前不能认定“三份 Cookie 可以稳定扩大并发”。三份文件名称分别为 7、8、9，虽然文件内容和部分辅助登录字段不同，但 SID、__Secure-1PSID、__Secure-3PSID、SAPISID 的值均相同，属于同一组核心登录会话，不能当作三组独立额度。相同会话也不能用于证明具体 Google 账号是否相同。

测试前在线登录检测通过；实际下载期间 yt-dlp 报告登录 Cookie 失效或被轮换，随后三份文件在原出口复查均返回未登录。本地 Cookie 到期时间仍在未来，因此不能依赖文件到期时间判断登录有效。未观察到明确的账号下载限额、HTTP 429 或 CAPTCHA；日志不足以确定是浏览器轮换、退出登录还是服务端撤销会话。

## 环境修复

主容器被重建后仅连接默认 IPv4 网络，但配置仍是 `youtube_source_address: '::'`，导致登录检查报 `[Errno 101] Network is unreachable`。恢复原有 `video-fixed-ipv6` 网络后，三份 Cookie 均通过在线检查。主实例出口保持 `2a06:f901:c001:100::fdb0:a5a2`，没有轮换 IP。

第二个下载实例已排空任务后停止，并将 Docker 自动重启策略设为 no；保留原数据卷和回滚容器。现在只保留主应用作为下载实例运行，MySQL 继续正常运行。

## 已修正的算法和页面

- 以 SID / PSID 等核心会话凭据合并并发和启动节奏；LOGIN_INFO 等辅助字段变化不会增加额度。列表显示真实核心会话组数和合并关系。
- 每会话从 1 个任务开始，至少 60 秒启动间隔；至少 5 次成功、并经过至少 10 分钟后，最多升至 2 个任务。请求间隔加 0～15 秒扰动以分散同时启动。
- 整个实例保留统一启动节奏，源站解析、传输、连接和限流额度继续共享。相同核心会话导出的文件不会获得更多额度。
- 可识别的网络异常回退到单任务并延长间隔；明确限流或登录验证使整个账号池停止。不会将受限任务换到另一个账号或 IP 重试。
- yt-dlp 首次提示 Cookie 失效时立即中断，避免继续尝试其他客户端或匿名下载。
- 页面逐行提供「检测登录」，显示结果、时间和出口；账号池显示并发、间隔、冷却和合并关系。池被拦截后提供人工恢复入口，必须停止实例、等待冷却、全部登录验证通过才可解除，不自动恢复任务。

最终配置：仍保存三份文件，合并为 1 组核心会话；实例任务上限调整为 2，实际从单任务预热。因三份登录均失效，实例及账号池保持暂停。测试模式仍是下载验证后删除临时文件，不保留视频素材。

## 后续所需

先补充一份可持续使用的有效登录 Cookie，验证单会话长期稳定性。若希望测试三个独立账号，请分别使用隔离的浏览器配置目录登录不同账号，导出后核对核心会话是否确实独立，不能只更换文件名或反复导出同一浏览器会话。

yt-dlp 官方说明指出：浏览器中打开的 YouTube 标签页可能轮换账号 Cookie。可按官方流程在新的私密窗口登录，在同一标签页进入 `https://www.youtube.com/robots.txt`，导出 youtube.com Cookie 后关闭该私密窗口，不再打开这段会话。关闭窗口不等于退出账号，主动退出会使登录凭据失效。此流程有助于减少浏览器轮换影响，仍不能保证会话不会被服务端撤销。

参考：[yt-dlp：导出 YouTube Cookie](https://github.com/yt-dlp/yt-dlp/wiki/Extractors#exporting-youtube-cookies)。

现阶段增加 CPU、内存、更多同段 IPv6 或相同会话的 Cookie 文件，无法解决已经确认的登录态问题。
