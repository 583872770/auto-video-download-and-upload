# 下载调度的使用与实现

系统设置新增“多渠道下载”。通常保持“复用解析浏览器”开启，并使用自动吞吐调节。浏览器上限先设 2～3；传输上限 16；本机媒体连接预算 32。上限只是允许探索的边界，实际用量由资源和测量结果决定。

没有额外网站时无需添加渠道。新增 Bergung / Cobalt 兼容网站必须填写真实网站及 API 地址，或从已实测的目录添加。标识 `bergung` 覆盖内置入口，其他标识添加入口。适配器继续使用 Bergung 画质、超时与成品校验。原有配置继续保留顺序回退；“同类渠道分流”只在同一种下载方式中选择入口；新增的“自动”策略允许在所有已启用下载方式中按吞吐、解析耗时、成功率及负载选择，不使用下载器顺序。只有后续领取的视频读取新策略。

“兼容”目前要求沿用 Cobalt 的网页元素和响应协议；支持 `redirect`、`tunnel` 和 YouTube 的双流 `local-processing + merge`，后者由 yt-dlp 下载同次解析所得的音视频，再由 FFmpeg 合并并校验。自动验证模式由网站处理验证；旧入口可以保留等待验证控件的模式。其他前端、播放列表和不支持的响应类型不能仅替换域名接入。每个新入口应先用少量视频验证，目录中的成功记录只是当日观察，不承诺持续可用或独立带宽。

所有未确认的媒体后台默认共用 `unverified-media` 带宽组；新增 Bergung 入口还默认共用 `bergung` 解析组与配额组。只有确认是独立资源时才拆组。相同 IP、不同域名、单次测速均不能证明独立。返回 Googlevideo 直链的任务在下载准入时归入 `youtube-origin`，避免把多个解析网站返回的同一源站当成多份容量。其他 CDN、重定向链和供应商内部配额仍需运营配置确认，不自动推断独立。

## 当前执行流程

1. 现有任务领取、实例选择、租约和停止意愿继续生效，每个视频只有一个任务所有者。
2. `channels.py` 生成渠道注册表；`channel_scheduler.py` 先选资源组，再选入口。自动模式使用 `预计耗时 = (平均解析秒数 + 64 MiB / 媒体传输 EWMA 速率) / 成功率 EWMA`，结合组负载、入口及后台在途任务数评分。统一参考文件大小，避免短视频占优。相同 API 无论前端域名或手动组配置如何，都强制共享后台任务、解析和配额许可。顺序模式保留原优先级；同类分流保留下载方式顺序。
3. 解析前申请共享解析/配额许可。Bergung 通过本机认证 JSON 协议交给 `parser_broker.py`；每个池槽位独占浏览器，同一入口及出口可复用。Clash 解析槽位使用独立监听器，不受下载工作进程轮换影响。网站和 API、浏览器程序、出口变化会重建会话；空闲 30 秒、使用 20 次或运行 300 秒后回收。
4. 就绪地址只留在本机内存；准备任务数量有界。下载前原子申请本机传输、上游传输、共享配额和媒体连接预算。上游繁忙最多等待 60 秒，随后释放当前准备结果、退回队列，避免长期保存未知有效期的签名链接。资源等待不扣视频重试次数。
5. 分片协议复用 yt-dlp，自适应分配每文件的媒体分片预算；普通 MP4/WebM 保持单连接传输。媒体连接预算是调度许可，网页、管理接口及代理自身连接另计。FFmpeg/第三方库内部连接不能承诺等于精确 TCP socket 数。
6. 保留原有媒体校验、磁盘预留、完成收据、去重及幂等统计。原有续传保护继续生效：多渠道回退或重启恢复时禁止盲目追加不同编码的内容。没有实现普通文件 Range 并行或跨渠道拼接；需要对象一致性、长度、可靠 206/Content-Range 等实测证据后再接入。

自动策略对未知入口每实例同时只允许一个解析试探；已有健康入口时约每 10 次调度给予一次冷入口机会。试探成功解析后释放试探额度，以便探索下一个入口，但该入口的首个文件完成前不再重复试探。每入口默认最多 4 个在途任务；每视频每轮最多尝试 3 个入口。所有入口仍共同受本机、上游组和共享配额约束，增加域名不会直接提高总容量。暂未证实独立的 Cobalt 后台继续共用 `unverified-media`，系统只依据总吞吐的增量逐步探索并发，不自动把它们拆为独立带宽。

## 反馈与退避

每 5 秒采样。网卡接收、媒体接收、校验成品速率分开显示；校验成品速率只有文件完成时增加，短窗口会波动。工作进程按槽位写有界、原子更新的本地计数，不保存媒体地址、Cookie 或令牌。

上游从 2 个传输开始，每轮至少观察 60 秒，仅在额度繁忙、有媒体流量且资源允许时增加 1 个。下一窗口增益不足 8% 即回退并冷却 120 秒。浏览器先从最多 2 个开始，在解析供给不足、CPU 较低及内存充足时试增 1 个；观察 120 秒，解析供给和媒体速率均未改善就回退。不会同时探测多个维度。CPU 持续高压、严重 CPU 压力、低可用内存或 I/O 压力会降低容量。

HTTP 429 与带 Retry-After 的 503 在相应解析组或媒体上游及配额组退避；支持秒数和 HTTP 日期。恢复期间限制为单次探测。单视频不可用不熔断整个上游。其他可重试错误沿用有界视频尝试次数，并对指数重试加抖动。yt-dlp 内部重试限为媒体/分片各 2 次、解析 1 次，避免与任务重试过度叠加。

自动模式的入口失败从约 15 秒开始指数退避，最高约 300 秒并添加抖动；429/Retry-After 优先遵从服务端等待。恢复后重新测量。数据库连接错误、任务租约、磁盘压力或本机依赖问题不会写入上游健康分数。不同 Cobalt API 的代理健康记录也分别计算，避免一个故障网站导致所有兼容入口被判为当前出口不可用。

容量控制另计 `upstream_failed`：仅媒体传输阶段的 HTTP 429/503 累计为上游失败；最近窗口至少 3 次且超过成功数时降低媒体额度。视频不可用、解析超时和网页验证失败只计普通失败，不据此降低共享带宽容量。阶段按实际媒体请求上下文判断，即使首个请求就在进度回调之前限流，也会归到媒体上游。

## 多实例与数据库预算

共享 MySQL 中新增 `download_resources`、`download_permits` 两张小表，通过短事务原子分配重叠许可；等待和下载不占事务。许可绑定任务 ID、worker owner 及有效任务租约，旧实例启动代号失效后不能再申请。不同实例仍各有独立的解析池、状态目录、磁盘与本机吞吐控制。使用同一数据库和组 ID 的**已升级实例**共用上游限制；同组不同配置取较小额度。旧版本实例不会参与新许可，需全部升级后才有完整共享约束。

租约失效能回收逻辑额度，原有心跳 watchdog 负责提前结束媒体进程，解析客户端断开会取消自己的页面。任意主机冻结/网络分区下，租约无法保证物理连接立刻消失；需要严格供应商总连接上限时，应增加统一出口网关。多容器同一物理机应配置 cgroup 配额，避免各实例分别把整台机器视为自己的资源。

`VIDEO_DB_POOL_SIZE`、`VIDEO_DB_MAX_OVERFLOW` 是**每进程**的池设置，不是视频并发上限。主服务建议 5+2；子工作进程默认 2+0，分别供业务写入及心跳使用。可通过 `VIDEO_WORKER_DB_POOL_SIZE`、`VIDEO_WORKER_DB_MAX_OVERFLOW` 调整子进程池。自动模式用 `VIDEO_WORKER_DB_CONNECTION_BUDGET`（默认 48）约束下载工作进程数，按每进程最大连接数预算；主服务、维护进程、其他实例/应用另留空间。手动模式保留用户指定进程数，应自行按此公式预算。

```text
数据库最大需求 ≈ Σ(各实例主服务池+维护池+下载进程数×子进程池上限)+其他应用连接
```

按多个 5～10 分钟窗口比较“校验成功的文件字节 / 总耗时”、完成数、按新执行尝试计算的失败率、429、CPU、内存、I/O 压力、数据库连接/等待。测试时保持视频、画质、出口和其他负载相近；先验证一个上游，再验证两个确认独立上游的增量。单次网卡峰值和累计失败总量的简单差值不足以证明优化效果。

代码验证重点在 `test_channel_scheduler.py`、`test_parser_broker.py`、`test_throughput.py` 和 `test_bergung.py`：跨进程/跨实例共享许可、别名与独立组、租约失效、原子准入、限流范围、解析断连取消、真实 Chromium 跨请求复用、无收益回退、数据库进程预算，以及原有下载/记账/停止回归。

`test_channel_scheduler_mysql.py` 可通过既有 `VIDEO_TEST_MYSQL_URL` 测试管理员配置，在自动创建、清理的独立 MySQL 库中运行同一组准入契约。MySQL `SUM(integer)` 返回 Decimal，统一转换成整数许可单位；不要只用 SQLite 验证数据库相关路径。

## 2026-10-29：300 Mbps 实例的解析复用与需求调度

自动策略继续把渠道、实际媒体上游、API/账户额度和本机资源作为重叠约束。新版本的 Bergung 解析槽位持有专用 asyncio 事件循环、Playwright/CDP 连接和页面；成功后移除本次响应监听器，下次按提交的视频 URL 校验响应。同一站点、API、画质及验证配置已成功设置时跳过重复设置页，但仍重新进入主页，清除前一次的界面状态。页面失败、取消、出口/站点变化、浏览器到期或空闲回收均重建或关闭连接。浏览器常驻仍占原来的跨进程槽位和磁盘预算。

传输等待任务在获得许可前就标记实际媒体上游；快照增加 `ready_transfer_count`、`oldest_ready_seconds`、各组 `ready` 和 `transfer_wait_resources`。阻塞原因区分全局、本机上游、共享上游、连接预算和配额，资源标识不包含媒体签名地址。等待线程每次准入重读动态额度，调大额度可以立即放行原任务，不必超时重新解析。

全局未满时不再仅因上游队列较长就扩大全局；全局已到配置上限时保留上游调节机会。上游有实际活动或等待需求、最近媒体字节增长且未达到带宽规划阈值时，每轮最多增加一个额度。没有足够活动传输的全局或上游试增不作为测速失败；有足够活动传输但试验无收益则退回，429/503 和共享配额继续触发原有退避。解析阶段 CPU 压力升高时优先减少解析槽位，持续压力、低内存和 I/O 压力仍收敛传输。

`bandwidth_mbps=300` 是目标容量；当前规划阈值为 90%，约 270 Mbps 媒体接收，预留协议/代理开销。此参数不是硬性网卡限速，也不保证公共上游提供目标速度。全局上限 16、媒体连接预算 32、浏览器上限 3 保持不变；MySQL 主服务 5+2、工作进程 2+0 和工作进程总预算 48 保持不变。不同机器按各自目标配置和资源反馈独立探索；共享数据库的上游/配额许可继续跨实例协调，本机许可仍按实例隔离。同一物理服务器上的多个独立实例尚未实现共同的网卡/CPU目标控制，不能给每个实例分别设置整机带宽并假定可相加。

不改变出口，不启用未经验证的媒体 Range 并行，不跨渠道拼接文件。验收应使用正常任务的媒体字节和校验后完成字节；网卡包含页面和代理开销，不能替代有效任务吞吐。

本版本已部署，实测数据、测试范围和后续优先级见[300 Mbps 部署与业务实测报告](300mbps-download-release-20261029.md)。
