# 美国服务器 yt-dlp 稳定性复测

本轮继续使用自有服务器 `88.210.37.181`、同一账号 Cookie、同一固定 IPv6，通过 yt-dlp 直连 YouTube 与 Google CDN。没有第三方解析、地址轮换或账号轮换。

## 已确认的问题

第一轮实际完成 171 个视频、77.09 GB 后，源站明确提示账号被限流，最长可能一小时。登录检查当时仍有效，响应也没有 HTTP 429。固定 IPv6、有效 Cookie 和每 5 秒启动并未避免这次限制，所以不能称为稳定方案。原始结果见 [第一轮报告](us-server-youtube-tuning-20261031.md)。

任务记录中的第一条账号限流完成于 12:37:11（视频 `g-LMh59dudM`），后续共 8 个视频记录相同限制，最后一个于 12:38:35 结束。171 个成功数是第一轮最终累计值，并不表示账号先成功 171 个再开始限流。新增熔断用来避免继续逐个消耗这些请求。

冷却期间不向 YouTube 发送测试请求。北京时间 13:50 之后才做一次登录及已知视频解析检查；如果限制未解除，保持暂停并记录，不能把登录通过当作视频访问恢复。

## 保护和试验设计

- yt-dlp `2026.10.26`；固定出口 `2a06:f901:c001:100::fdb0:a5a2`，应用配置 `youtube_source_address: '::'`。
- 每 60 秒最多启动一个视频；解析上限 1，分片并发 1。
- 启用等价于 yt-dlp `-t sleep` 的等待：解析请求之间 0.75 秒；每个媒体文件开始前 10～20 秒；字幕文件前 5 秒。视频、音频可能分别等待，不限制已开始文件的字节传输速度。这是下载器预设，不是 YouTube 的安全额度。
- 先单路观察 30 分钟，完成当前任务后停止；再两路传输观察 90 分钟。解析频率保持不变，避免同时增加请求频率与传输并发。
- 明确账号限流立即停止本实例领取，当前失败任务回队且不消耗失败次数，保留至少一小时共享冷却，等待人工检查；不自动接着测试另一视频或另一渠道。其他已取得执行资格的并行任务可能尚在收尾，停止不是撤回已发送的请求。
- 机器人验证、登录失效仍保留原暂停保护。HTTP 429 / 503 进入源站共享冷却，本次观察控制器遇到任何源站冷却也停止测试。
- 保持原 `storage_mode=test`：真实下载并校验后删除视频，保留结果与统计。

观测只读取自有应用数据库、进度和主机资源，不向第三方传递 Cookie。账号限流检查采用明确文本，通用 Video unavailable 保留未知归因。

## 验证记录

本轮 112 项相关回归测试通过；账号限流的测试覆盖共享冷却、任务回队、实例停止领取及不继续领取下一视频。真实 Chromium 页面检查覆盖账号限流说明、新开关保存回读和手机布局，无页面错误或横向溢出。镜像启动检查通过。

镜像 `youtube-downloader-local-app:stable-v2-20261031`；部署备份及观测数据在服务器 `/root/video-stability-20261031`，仅 root 可访问。旧应用保留为停止状态的 `youtube-downloader-local-app-before-stability`，没有删除数据卷。原始镜像和第一轮备份仍保留。

## 最终结果与推荐

北京时间 13:50 的登录和视频预检通过，同一个已知视频解析出 123 个格式。13:51:23 开始下载观察，15:53:26 完成两阶段、结束收尾并按推荐配置恢复队列。

| 阶段 | 时间（含收尾） | 成功 | 完成字节 | 失败 | 平均媒体吞吐 |
|---|---|---:|---:|---:|---:|
| 单路，30 分钟观察 | 13:51:23–14:22:29 | 24 | 10.24 GB | 0 | 43.15 Mbps |
| 两路，90 分钟观察 | 14:22:36–15:53:21 | 83 | 63.49 GB | 2 | 90.53 Mbps |
| 合计 | 约 2 小时 | **107** | **73.74 GB** | **2** | 不合并不同阶段口径 |

两个失败均为源站明确的内容限制：`R2nqMBrqx6o` 私有；`nqLOuhJAAFw` 被上传者删除。观察窗口没有新增账号限流、验证码、机器人验证或源站共享冷却。两阶段视频集合不同，不能据此声称两路具有确定的倍数提速。

吞吐为约 30 秒采样的时间加权媒体接收值，单路覆盖 1764.2 秒，两路覆盖 5365.6 秒；阶段结束后完成字节包含收尾文件，因此不直接拿该字节数除以媒体采样时长。两路平均 CPU 指标约 15.7%，I/O 压力约 0.6%，没有资源压力证据要求增加服务器。

**当前最终推荐为下表，已保存并继续执行现有队列。它是本次验证通过的保守配置，不是永不被限流的承诺。**

| 配置 | 值 |
|---|---|
| 下载器 | 自有服务器 yt-dlp 2026.10.26 |
| 网络 | 直连，固定 IPv6，同一 Cookie |
| 视频启动最小间隔 | 60 秒，实例内共享 |
| yt-dlp sleep 预设 | 开启 |
| 传输 / 工作进程目标上限 | 2，自动调节可有少量准备任务 |
| 解析 / 分片并发 | 1 / 1 |
| 本机 / 共享连接预算 | 4 / 4 |
| 匿名重试 | 关闭，明确账号限流即使开启也不匿名重试 |
| HTTP 429 冷却 | 至少 300 秒，更长 Retry-After 优先 |
| 明确账号限流 | 至少 3600 秒共享冷却，实例暂停，任务回队，人工核对后恢复 |
| 存储 | 保持 test，校验后删除视频 |

当前暂不再提高并发或缩短启动间隔。第一轮更快但触发账号限流；本轮降低请求频率并加入等待后通过约两小时观察。由于同时改变了频率、等待、并发并经过冷却，无法将改善归因于单独一个参数。

本轮控制器已正常完成退出，应用自带的熔断继续有效。16 个部署文件的 SHA-256 与本地核对一致；最终相关策略测试 20 项通过。后续推荐连续观察 24 小时的限制次数与完成率，再决定是否调整，而非仅按瞬时速度加压。

## 长期判断边界

即使两小时观察没有触发限制，也只能证明该账号、该出口、该视频集合在这个窗口内通过。账号是否还被其他程序使用、YouTube 配额变化、视频权限与大小均会改变结果，不能保证永远不触发验证。

不建议为同一账号的限流购买更多 IP。更有用的信息是是否有其他下载程序共享账号、商家的持续带宽和月流量额度。若要永久保存视频，需要另行规划存储；测试模式的成功数量不代表视频保留在磁盘上。

后续重建应用需要同时使用 `compose.ipv6.yaml`。详见 [IPv6 部署指南](fixed-ipv6-youtube.md)。
