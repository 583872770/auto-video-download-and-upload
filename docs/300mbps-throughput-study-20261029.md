# 300 Mbps 下载吞吐研究与实施顺序

研究日期：2026-10-29。目标是尽快完成有效视频下载，300 Mbps 等于 37.5 MB/s；浏览器页面、代理封装、重传和重复下载不能充当有效任务吞吐。

后续进展：本文保留最初研究阶段的事实与建议；同日已完成解析复用和需求调度改造并部署，15 分钟业务实测及最终健康结果见[部署与业务实测报告](300mbps-download-release-20261029.md)。下文“本轮只做读取”等表述仅指最初研究阶段。

本轮只做服务器读取、正常任务采样和有界公共文件接收测试。没有更换线上镜像、修改下载策略或切换代理选择器。测试没有写入生产任务或交付账本，收到的测试字节直接丢弃。代码审查和 CPU 控制候选修改在复核后未保留；不能仅因容器 CPU 低于主机 CPU 就忽略真实的共享 CPU 争用。

## 已确认的事实

| 项目 | 现场结果 | 解释与限制 |
| --- | --- | --- |
| 计算资源 | Intel Celeron J4125，4 核，内存约 7.36 GiB | 属于低功耗 CPU，机器还运行其他服务；不能只按核数推断浏览器处理能力 |
| Docker 限额 | CPU quota、内存限制和 CPU affinity 均未额外设置 | 本实例没有被 Docker 配置人为限为 1–2 核；当前看到的 4 核来自主机 |
| 网卡 | eno1，1000 Mb/s，全双工 | 排除本机百兆协商上限；不证明公网路径持续提供 300 Mbps |
| 磁盘 | 118 GB 非旋转设备；短时采样利用率约 7.7–10%，写等待约 1.2–1.4 ms | 这个轻负载样本没有显示磁盘饱和，尚未验证满速下载加合并时的磁盘余量 |
| 本服务 CPU | 连续 45 秒 cgroup usage 差分，约占全机容量 55.86% | 包含采样期间已经退出的工作进程，比仅统计存活进程更完整；与上一轮不同窗口的 76.7% 主机 CPU 不能直接作差 |
| CPU 等待 | 本服务 cgroup CPU PSI some avg10 约 16–37%，full 约 3–6% | 确有调度等待，不能把主机 CPU 全部视为无关负载 |
| 在途状态 | 多个快照有 2–3 个 `waiting_transfer`，同时只有 1 个 `downloading` | 问题会从解析供给不足转为已就绪任务无法获得传输许可，需要分别处理 |
| 传输额度 | 上述窗口全局额度 2、共享媒体组额度 1，随后媒体组试增至 2 | 配置上限 16/32 不等于实际使用 16/32；上游独立性尚未确认 |
| 实际媒体接收 | 上述单传输阶段滚动约 93–97 Mbps | 这个任务路径存在约百兆的接收能力；不能据此保证三个任务一定达到 300 Mbps |
| 数据库 | 前一轮健康检查总连接 25/500，无新增连接失败 | 当前没有证据需要靠放大数据库连接池提速 |

此前 4 分钟窗口的网卡平均接收为 81.74 Mbps；按下载进度计数的媒体接收约 76.96 Mbps；窗口内完成并校验的文件折算为 41.46 Mbps。后两个口径不同：有些字节仍属于在途文件，也可能包含重新下载；不能将差额全部认定为浪费或解析开销。

## 有界线路测试

普通文件通过 urllib 从容器网络读取，每连接最多读取 32 MB，约 20–25 秒后结束，不落盘，生产下载保持运行。测试源会限流，短窗口包含连接建立、TLS 和慢启动，不构成严格 A/B 基准。

| 公共测试路径 | 结果 |
| --- | --- |
| 直连清华 Ubuntu 镜像，单连接 | 45.03 Mbps，32 MB 完整收到 |
| 同一镜像，4 连接 | 总计约 6.74 Mbps，时间预算内均未完成；不能确定是路径波动还是共享限速 |
| 当前代理到 OVH，单连接 | 55.10 Mbps，32 MB 完整收到 |
| 同一 OVH 路径，4 连接 | 三个连接完成，一个返回 HTTP 429；测试载荷均值 94.22 Mbps，同期容器含正常工作接收约 170.95 Mbps。收到 429 后未重试该源 |
| 直连 Mozilla 下载，另一轮多源测试 | 32 MB 约 2.13 秒，单请求约 120.14 Mbps |
| 当前代理到 Mozilla，同轮后续测试 | 32 MB 约 6.45 秒，单请求约 39.70 Mbps |

Cloudflare 测试入口没有得到有效测试载荷，已排除。公共源的 206/Content-Range 验证只说明这些测试文件的 Range 行为，不能移用到 Cobalt 媒体地址。

结论：尚未用这些公共测试证明公网路径持续提供 300 Mbps；也不能把某一个源的 45/95 Mbps 当成服务器的固定上限。代理并非对所有目的站都更快，多域名也不自动代表独立容量。应先确定良好上游、出口及实际媒体路径，再逐步扩大准入。

## 从 300 Mbps 反推需要的供给

不计协议开销，填充 300 Mbps 所需传输数量近似为 `ceil(300 / 单传输有效 Mbps)`：

| 每个传输可持续速率 | 需要的传输数 |
| --- | --- |
| 10 Mbps | 30 |
| 30 Mbps | 10 |
| 50 Mbps | 6 |
| 100 Mbps | 3 |

这些是容量规划示例，前提是上游和出口总带宽没有共享瓶颈。若共享账户或同一后台总共只给 100 Mbps，开 30 个连接也不会得到 300 Mbps。

解析供给同样必须匹配文件大小。以平均文件 **250 MB** 为例（仅用于规划，并不代表所有任务）：37.5 MB/s 要求约 **9 个有效下载地址/分钟**。两个解析槽位平均每个应在约 13 秒内产出一个有效地址；三个槽位约 20 秒。若每个解析需要 50 秒，单靠两个浏览器就无法持续供应这个目标，即使瞬间有一个大文件能下载很快。

上一轮 4 分钟完成文件的均值接近 250 MB，但完成窗口受跨窗口任务和大小分布影响；实际调度应使用近期文件大小分布及解析成功率，而非把这个均值写死。

## 建议的实现顺序

### 1. 让控制器识别已就绪任务和每条许可的限制来源

改造 `webapp/throughput.py`、`webapp/channel_scheduler.py` 和 `web_worker.py`：

- 记录每组的 `ready_count`、估计剩余字节、最老就绪时长、预计链接有效期，以及实际阻塞资源。等待全局传输、上游额度、账户配额和连接预算应能区分。
- 解析完成后就更新实际媒体组，使 Googlevideo 直链等待时也归入 `youtube-origin`。域名、实际媒体路径和供应商配额共同约束；未验证资源继续共享总预算。
- 每次只试增一个有效传输许可，协调全局和目标组的额度；不能只提高全局额度，留下组额度仍为 1。相同 API 和账户配额保持硬约束。
- 正常时至少观察一个足够的传输窗口；排除浏览器刚启动、文件结束及无就绪任务的窗口，避免把任务切换误判成扩容无收益。先探索 2→3→4，之后按收益继续，不能直接把上限 16 当目标。
- 用媒体速率判断短期增益，结合已校验字节、失败及重下成本判断长期收益。带宽目标已知为 300，应区分公网接收预算和媒体有效数据目标，而非直接把控制器阈值设为 300 后期待自动满速。

### 2. 浏览器和下载分别调节，减少重复准备

当前 `BrowserSession` 复用浏览器进程，但 Bergung 每次仍建立 Playwright/CDP 会话、新建页面、依次访问设置页及主页，解析后关闭页面。

下一版可让 broker 槽位持有专用事件循环、Playwright 连接和页面，同一渠道、出口及配置的连续任务复用页面与已确认设置。渠道、出口、画质变化或页面失效时重建；正常网站验证失效时按网站流程重新验证。

维护有界的就绪缓冲，初始可按目标接收速度覆盖约 10–20 秒的字节量规划（300 Mbps 时约 375–750 MB），同时受链接实际 TTL、每渠道配额和持有任务数限制。未知文件大小用保守估计，未知 TTL 的链接不宜预先囤积。

- 已有就绪任务时，优先填充允许的传输额度，并停止继续扩大解析队列；减少准备完却因等待超时而重复解析的情况。
- 就绪队列耗尽且传输空闲时，先增加解析效率；仅在 CPU、内存允许且有实测收益时增加一个浏览器。
- 同机 CPU 压力升高时，分别观察主机 CPU、容器 CPU、CPU PSI 和任务阶段。若压力来自新浏览器启动，可先抑制新解析、保留已有传输；若来自代理/传输处理，则需要收敛传输。
- 内存、磁盘空间和严重 I/O 压力继续作为硬保护。不能通过忽略主机 CPU 来追求表面速度。

### 3. 按实际媒体吞吐选择出口及上游

以“渠道/实际媒体组 × 出口”统计媒体速度、解析延迟、成功率、429/503、超时及重下量。选择预计完成更快且有资源余量的路径；延迟小或 TCP 连通不能代替媒体测速。

对于允许直接访问的媒体，比较直连与代理的真实样本；浏览器解析与媒体传输不一定永远需要走同一条路径，但签名、验证或出口绑定未确认时，继续使用原出口，不直接切换。

共享节点供应商也可能有账户总带宽。不同节点名字、不同 Cobalt 前端和不同 CDN 域名均不自动证明独立资源。先在固定总并发下比较新增路径的总吞吐增量，再决定是否拆分资源组；测试相关性只是证据之一，不能代替供应商配额信息。

### 4. 最后评估单文件 Range 并行

先使用不同视频的任务级并行。只有某条实际媒体地址通过稳定对象身份、正确 206/Content-Range、长度和随机范围一致性验证，且单连接受限、上游仍有余量时，才试单文件 2 条连接，再考虑 4 条。

音频、视频、HLS/DASH、Range 都纳入现有 32 条媒体连接预算。跨渠道拼接继续关闭，除非能证明完整内容逐字节一致。公共测速文件支持 Range 不代表生产媒体也支持。

## 起始参数及验证

建议保留实例上限 16、媒体连接预算 32、浏览器上限 3，先优化实际额度和解析效率。已知公网目标为 300 Mbps；有效媒体探索可先以约 270–285 Mbps 为规划区间，再按实际封装开销确定，不能保证任何公共上游始终提供该速率。数据库池仍沿用现有主服务 5+2、工作进程 2+0、工作进程连接预算 48；共享数据库的其他实例和服务另计。

同一批视频、画质和出口交叉比较，每组预热后观察至少 15–30 分钟，至少完成足够多的文件。先测持久解析，再测 2/3/4 个有效传输，再测不同健康出口/上游的增量。记录：

- 物理网卡唯一接收速率、媒体接收、成功成品字节/总耗时，避免 Docker bridge 与 veth 重复计数。
- 解析成功地址/分钟、每组就绪字节、传输空闲秒数、按限制来源分组的等待时长。
- 容器和主机 CPU、CPU/IO PSI、内存和 swap-in/out、磁盘等待及空间。
- 新执行尝试的失败率、429/503、重试下载量、MySQL 连接池等待与租约错误。

候选方案只有在完成吞吐增加且失败、资源压力受控时保留。瞬时网卡 300 Mbps 或额外测速流量不算业务验收通过。

研究结束时只读读取到的线上控制状态为：实际传输额度 `7`、共享 `unverified-media` 组额度 `4`、工作进程 `8`、浏览器 `2`，媒体接收滚动值约 `121.07 Mbps`，网卡接收滚动值约 `151.30 Mbps`，CPU `79.6%`，I/O 压力 `6.67`。这比之前额度 1～2 的窗口明显提高，但距离 300 Mbps 仍约差一倍，且该读数是短时间滚动统计，不是稳定验收结果。

当前正式留存若只有约 33 GiB 空间，300 Mbps 持续写入约 15 分钟就会接近空间预算；正式模式必须让上传、删除或归档持续跟上。测试模式仍为校验后清理，两种模式不能混为交付量。

若经过以上优化仍有充足就绪任务、健康上游/出口可提供目标速率，但 J4125 长期 CPU 饱和，再考虑更强 CPU 的服务器或独立解析计算资源。链接出口绑定和任务租约必须保持正确；在同一台机器多开下载容器不会增加物理 CPU 或公网带宽。

本地原始测量：`.cache/validation/cobalt/diagnose-300-live.jsonl`、`probe-300-network.jsonl`、`probe-300-fallback.jsonl`、`probe-300-multiorigin.jsonl`。它们包含具体请求窗口及失败样本，未将短时测速写成持续性能承诺。
