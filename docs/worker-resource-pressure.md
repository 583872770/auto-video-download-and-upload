# 下载进程资源保护与运行状态

本轮修复针对“本机下载进程已占满”反复出现但无法看出真实动态上限的问题。代码已修改并验证，尚未部署。

## I/O 压力的作用范围

采集逻辑优先读取当前进程所属 cgroup 的 `io.pressure`，覆盖常见 Docker cgroup 命名空间以及宿主机上的嵌套服务进程组。嵌套组的指标不可用时，不用可见父组冒充当前组。整机 `/proc/pressure/io` 另行采集为参考，不会覆盖有效的当前进程组指标。

没有可用进程组 PSI 的旧内核或环境仍回退整机采样，页面明确标记“整机 I/O 压力（回退采样）”。两类指标均不可用时记录未知，不显示为 0%；CPU 和内存保护继续生效。I/O 指标来源切换时清除连续高压采样计数，避免把不同范围的样本累加。

指标继续使用 `some avg10`：约 10 秒平滑平均中，至少一个任务因 I/O 阻塞的时间比例。数值不等于磁盘利用率、剩余空间或带宽使用率。

## 资源保护规则

阈值与展示所需的规则统一放在 `webapp/resource_pressure.py`，本轮没有新增页面或环境变量设置。原有主要规则保留：

- CPU ≥90% 或选定范围的 I/O 压力 ≥15%，连续三次高压采样后进入保护；CPU ≥97% 或紧急内存不足可直接认定压力。
- Cookie 池进程数每隔至少 60 秒可以缩减至原来的 80%，向下取整且至少保留一个进程。正在执行的任务继续完成，之后退出多余进程。
- 释放保护后，每隔至少 60 秒最多恢复一个进程。恢复需要 CPU <80%、已取得的 I/O 压力 <15%、可用内存达到 512 MiB 与总内存 12% 中的较大值。
- 本轮补齐恢复时的 I/O 水位检查：刚开始出现高 I/O、但还没有累计三次高压样本时，也不会反向增加进程。

常规上限继续综合账号会话容量、配置上限、传输与准备容量、内存及数据库连接预算。资源保护可能让当前动态上限暂时低于常规上限。来源与规则变化没有修改 Cookie 的启动频率、账号绑定、账号冷却或原有任务准入许可。

## 页面说明

账号卡片上方集中展示：

- 当前任务进程占用 / 动态上限、常规上限和配置上限。
- 实际传输、等待 / 解析、后处理分别占用多少任务进程。
- 最近一次资源缩容的前后数量、触发指标、数值和阈值；恢复期间保留该原因。
- 当前 I/O 压力的来源、数值，以及整机参考值。
- 恢复阈值、当前未满足的条件及距下次具备调整资格的检查时间。

倒计时表示调整间隔，不承诺时间到即增加进程；检查时仍要满足最新资源条件。若常规容量变化后逐步扩容而没有资源缩容记录，显示“进程上限逐步恢复中”，不虚构历史压力原因。采样过期、配置不匹配或实例离线时不展示旧的实时进程状态与恢复预测。

空闲账号卡片的进程等待原因补充真实占用与动态上限。已有任务的账号不重复列出这条全实例等待提示。全实例瓶颈说明也区分资源保护和常规配置上限，避免在保护缩容时建议继续提高配置上限。

状态沿用现有吞吐快照和页面刷新，无新增数据库查询或前端轮询请求。
