## 已确认的首要浪费：留样查询缺少任务索引

`webapp/delivery/samples.py` 的 `capture()` 在测试任务结束整理留样时，执行按 `task_id + job_id + test_mode + instance_id` 查询 `delivery_artifacts` 全行的 SQL。表只有主键、序号、任务组与序号、实例与序号索引，没有 `task_id` 索引。

服务器上该表统计估计约 47.5 万条记录。只读 `EXPLAIN FORMAT=JSON` 显示查询使用 `ix_delivery_artifacts_job_seq`，仅用 `job_id` 定位，估计每次检查约 270,790 条候选，再过滤视频执行 ID。这里是优化器估计，不是一次实际查询的精确扫描计数。

独立 21.36 秒的 Performance Schema 表 I/O 增量显示，`delivery_artifacts` 读取 2,690,617 行、写入 16 次，表操作累计等待约 17.34 秒。同窗口任务表只读取 3,235 行。18 次活动 SQL 快照中，13 次直接看到上述留样查询；多次同一执行持续约 2～3.4 秒。实现位置、实际执行和缺失索引三者对应，说明这是当前明确且随着测试历史增长会加重的浪费。

`capture()` 还先查询产物，再判断已有留样是否 ready、快速测试是否关闭留样；这些分支存在避免查询的空间。建议首先为 `delivery_artifacts.task_id` 增加索引，保留其他实例与任务归属过滤；再将已完成留样及关闭留样的判断前移。一次视频应只读取自身的少量产物，避免反复遍历整个客户任务的历史文件。需要同时维护当前 schema 声明并在隔离 MySQL 验证执行计划及留样、统计、清理行为，之后再发布，不能仅改服务器索引而遗漏源码。

MySQL 的统计摘要槽已满：`Performance_schema_digest_lost` 约 78.3 万，未归类摘要累计检查约 157 亿行。常规按 SQL 摘要排行可能漏掉该新语句，不能因排行榜没有它便认定不存在慢查询。此次以活动语句和表操作增量交叉确认，没有清空监控统计或修改 MySQL 配置。

## 其他优化优先级

后续下载进程调用栈已进一步定位终端进度格式化热点，见[专项采样与隔离比较](2026-11-23-download-worker-profile.md)。下列其他候选项的优先级应结合该实测更新。

1. **先消除上述扫描。** MySQL 在本窗口平均占整机约 15%，峰值更高；这并不代表补索引一定能消除全部 MySQL CPU。预期可减少无效计算及测试收尾等待，实际收益需发布后同口径测量。
2. **再减少状态路径的重复数据库读取。** 40.75 秒窗口中，实例整行读取约 31.49 次/秒、数据库时间查询约 25.28 次/秒，总 Questions 约 246 次/秒。Redis 已降低高频写入，但进度回调仍执行实例/租约所有权读取。可按职责缩小读取字段、复用同一事务中的实例记录和数据库时间，使用有期限的显示缓存；不能把 Redis 当作任务领取、停止或续租的授权依据。
3. **按解析和传输阶段分别控制新增工作，降低 CPU 峰值。** Node 与网络进程叠加是满载的重要来源；现有启动门控在 Cookie 准入后释放，不覆盖整个解析阶段，且一个 Node 运行时自身也会使用多个线程。已有 resolve/transfer 许可需先按实测评估，不能再重复添加同义限流，也不建议未经对照就把全部下载并发砍半。应先修数据库浪费，再判断解析限制是否仍有必要。
4. **最后再考虑转码或硬件。** 本窗口 FFmpeg 与本地处理占比低于下载和数据库，不是第一优先项。两地拆分数据库或增加 CPU 可以缓解资源竞争，但不能代替修复扫描。

验收同时观察任务成功数、完成产物字节、媒体接收速度、每 GiB CPU 秒和排队延迟。节省出的 CPU 可能被更多有效下载利用，因此不以“CPU 必须明显下降”作为唯一通过条件。本次没有进行变更或前后对照实验，不能承诺具体提速比例。
