# 洛杉矶 CPU 波动排查

## 结论与观测范围

2026-11-23 北京时间 16:21:32–16:27:32，对洛杉矶 `216.227.169.90` 做约 360.53 秒自然运行采样，共 351 个间隔。CPU 平均 64.84%，最低 20.99%，最高 99.75%，P95 为 92.08%。这是短时满载与低负载交替，不能将单个 100% 截图解释为一直满载。

当前主要原因是下载任务在等待、解析、接收数据之间切换，下载数据处理负载出现波峰；FFmpeg 和本地处理叠加放大波峰。自动资源反馈另会在分钟尺度改变并发，形成负载下降、恢复的过程。尚不能根据本轮观测把 Node 列为主要原因。

只读排查，未修改业务实现、配置、数据库结构或镜像，未暂停、重启或部署应用。采样镜像为 `youtube-downloader-app:player-cache-final-20261123-r64`，健康、重启次数 0。服务器 4 核；本文 CPU 均按整机 100% 口径，单核满载约等于本文的 25%，与进程工具单核 100% 的口径不同。

## 下载与本地处理的波峰

| 指标 | 整机 CPU <50% 的样本 | 整机 CPU ≥90% 的样本 |
| --- | ---: | ---: |
| 样本数 | 76 | 27 |
| 整机 CPU 均值 | 39.46% | 93.74% |
| download + regular 工作进程 CPU | 26.81% | 47.91% |
| 本地处理 Python + FFmpeg CPU | 1.61% | 11.20% |
| Web/调度主进程 CPU | 2.01% | 8.89% |
| 实际网卡接收量 | 614 Mbps | 814 Mbps |
| downloading 阶段任务数均值 | 4.72 | 5.90 |
| waiting_request 阶段任务数均值 | 17.27 | 15.54 |
| extracting 阶段任务数均值 | 0.78 | 1.62 |

任务上限 24 不代表 24 个任务一直同时传输。阶段数据来自约 5 秒刷新的运行快照，不能据此断言某一秒的精确任务数。`waiting_request` 既包括网络/上游等待，也包括当前启用的请求间隔与文件开始前等待；不是所有等待都代表故障或上游变慢。

CPU 最高的一个间隔中，下载/regular 工作进程合计约 67.20%，主进程 11.77%，FFmpeg 9.56%，同期网卡接收约 928 Mbps。下载过程仍需要请求与响应处理、TLS、数据缓冲、分片调度、文件写入和进度回调；不能按“只是下载”推断为几乎不消耗 CPU。本轮进程相关性支持下载是最大波动来源，但没有为这些底层操作逐一分配精确 CPU 比例。

全部窗口中，下载/regular 进程平均约 36.56%，本地处理与 FFmpeg 约 6.77%，主进程约 3.91%。高峰时三者叠加，等待和处理结束时回落。主进程有短时高占用，但不能据此称其为整体第一来源。

## 自动并发反馈

当前实际配置为任务上限 24、账号 33、分片并发 4、本地处理并发 2、单账号会话上限 1、账号启动间隔 0，并启用 YouTube 等待预设。没有沿用早前版本的配置假设。

| 北京时间 | 动态任务上限 | 控制器 CPU 样本 | 应用 cgroup I/O PSI avg10 | 说明 |
| --- | ---: | ---: | ---: | --- |
| 16:21:32 起始 | 24 | 76.5% | 4.34% | 当前配置上限 |
| 16:24:06 | 24 → 21 | 74.4% | 18.25% | I/O 超过 15% 阈值触发降载 |
| 16:25:12 | 21 → 23 | 54.5% | 3.16% | 压力恢复后增加 2 |
| 16:26:17 | 23 → 24 | 62.0% | 3.95% | 恢复到配置上限 |

I/O PSI 是任务因 I/O 等待受阻的压力指标，18.25% 不是磁盘空间使用率，也不是 CPU 使用率。本次下降由 I/O 触发，不能说成 CPU 达到阈值才下降。运行快照还保留了一次窗口之前的降载记录，不把它重复计入本轮事件。

代码每约 5 秒采样，CPU 高阈值 90%、紧急阈值 97%、恢复阈值 80%，I/O 高阈值 15%；普通高压需连续 3 个样本，紧急 CPU 可更快触发；动态调整间隔至少 60 秒，降载系数 0.9，恢复每次加 2。降载逐步停止补充名额，已有任务继续收尾。因此反馈会造成分钟尺度的负载起伏，但它首先是在响应负载和 I/O 压力，不能把它当成全部波动的唯一根因。

## 其他负载与边界

应用 cgroup CPU 平均 53.85%，MySQL 2.82%，Redis 0.27%，字幕 PO 服务约 0.02%。采样识别到的 Node 平均约 0.47%，高 CPU 桶内约 0.93%；短生命周期进程可能在两次采样间结束，该数字是可观测下界，不能当成完整精确 CPU 时间。但没有证据支持它是本轮整机波动的主要来源，也不支持立即限制 Node 并发。

整机 CPU 模式均值：用户态约 36.23%、内核态 20.13%、软中断 8.47%；I/O wait 约 5.25%，后者属于等待，不计入本文 busy CPU。steal 约 0.07%，没有明显宿主机抢占证据。可用内存约 4.72–5.88 GiB，无 swap 使用；本轮没有内存耗尽证据。

每约 1 秒的进程采样可能漏掉短命进程退出前的最后一段 CPU，因此进程分类之和不与 cgroup 强制对齐。采样脚本自身 CPU 约 8.15 秒，约占整机 0.56%；自然采样与之后的调用栈诊断严格分开，工具下载和调用栈采样不计入上述 6 分钟结果。当前没有相同视频、相同阶段的受控前后对照，不能用这些数据承诺调整后 CPU 或下载速度改善多少。

## 主进程调用栈与可优化项

自然采样结束后，单独使用临时 `py-spy 0.4.1` 对 Python 主进程（宿主 PID 3632098）做 13 Hz、指定时长 90 秒的 `--gil --nonblocking --threads --full-filenames` 原始栈采样，不读取局部变量。容器 init PID 3632065 不是 Python 主进程；初次以 init 为目标时工具返回无法识别 Python，未产生有效样本，改用自然采样确认的 Python PID 后成功。

工具输出 89 个有效持锁样本、35 次读取错误。外部实际计时约 85.35 秒，该独立窗口主进程 CPU 平均占整机 3.87%，工具 CPU 合计约 0.32 秒。非阻塞模式会出现读取失败；样本少，仅用来定位重复路径，不把持锁样本比例当成精确 CPU 时间，更不换算为整机可节省比例。

| Python 主进程路径 | 持锁样本数 | 说明 |
| --- | ---: | --- |
| 日志清理 `prune_disk_logs` | 38 | 其中路径安全核对所在行 10、单文件及 offset 大小核对 7、整目录大小核对 5、清理空分片目录的 stat 所在行 10 |
| 磁盘预算 `DiskBudget` | 11 | 独立于上行分类，包含用量核对等 |

维护线程合计 52 个样本，调度线程 37 个；该轮未采到 HTTP 请求线程持锁活动，不将其误称为用户页面请求热点。

已核对线上与本地 `maintenance.py`、`disk_budget.py`、`runtime/supervisor.py`、`application.py`、`Utils/config.py` SHA256 一致。日志维护每 30 秒执行一次：递归列出日志、分批查询任务状态、逐文件核对路径与占用，再遍历日志目录算总量、扫描孤立 offset 与空分片目录。同一周期有重复目录访问，调用栈已采到这些路径。收尾时日志维护快照保留 1166 个任务日志，目标上限 2048，最近删除 4 个，数据库可用、并非低空间清理。

`DiskBudget._refresh_usage` 本身已有共享用量缓存和扫描锁，不能称其完全没有缓存。继续优化应针对跨维护流程的重复读取、扫描范围和增量更新，保留缓存失效、配额核对及资源不足时的保护。

建议优先级：

1. 日志维护改为有时间预算的增量检查；在一次检查中复用文件元数据和占用统计，记录需检查的日志/目录，减少每 30 秒重新扫描全部分片。保留运行任务保护、路径安全检查、容量与保留期限，以及周期性完整校验。
2. 复用配置解析和同一调度轮的实例配置结果，按配置版本或修改时间失效，避免每轮重复 YAML 解析和相同实例查询。不要缓存任务所有权、停止/暂停、资源准入等必须及时生效的控制结果。
3. 完成扫描精简后，再按下载阶段、分片并发和 I/O 压力进行同条件测量，评估资源反馈恢复节奏。当前只观察到本窗口一次下降与两次恢复，不能断言控制器长期频繁抖动，也不宜为图表平稳直接取消保护或大幅减少任务数。

当前证据不支持优先限制 Node。改动后的验收应同时比较整机/各进程 CPU、每 GiB CPU 秒、实际媒体接收量、任务完成率和错误，不能只用 CPU 曲线更低判断效果。以上为分析建议，本轮未实施。
