# 下载吞吐与异构服务器扩容诊断

2026-10-29，北京时间约 09:13–09:24，通过 SSH 检查正在运行的 `youtube-downloader-app-1`、宿主机、数据库和任务日志。包含两段各 60 秒的资源/流量采样，以及经现有代理端口进行的小流量站点探测。没有修改线上配置、业务数据或下载策略，没有重启服务。探测不创建第三方转换任务、不切换代理节点，不进行大文件带宽压测。

## 结论

目前最明确的吞吐损耗是：**异常代理路径仍参与轮换，任务等待浏览器和网站验证时占用完整下载名额，失败后又串行尝试多个下载器。** 8 个运行任务经常只有 1–2 个实际传输文件。优化应先恢复有效传输任务的供应，再根据资源和成功吞吐自动调节各阶段并发。

后续不同配置服务器应各自运行反馈控制器；集群还要消除固定全局并发预算和领取事务串行化带来的扩容上限。不能承诺仅修改并发或 Docker 参数即可跑满公网带宽。

## 当前配置与瓶颈证据

线上实例配置为：8 个下载进程、2 个共享浏览器、分片并发 3、测试模式；下载器顺序为 **Bergung → yt5s → yt1d → downmp3**，各自请求 best 画质。Clash 每处理 1 个视频轮换节点，失败也计数，候选有洛杉矶、新加坡、凤凰城。全局并发预算为 32。

全局队列计数约 135.5 万 queued，running 为 8；queued 包括不同任务和运行意愿，不能据总数判断全部已释放待执行。采样时只有当前服务器的实例在线，其他登记实例已离线。

### 1. 一个现有代理路径出现跨站 TLS 失败

通过已经存在的监听端口请求四个站点首页，每个响应最多读取 1 KiB，没有改节点选择：

| 路径对应的节点 | Bergung | yt5s | yt1d | p.savenow.to |
|---|---|---|---|---|
| 美国洛杉矶-2 | 200 / 0.91s | 200 / 0.55s | 200 / 0.58s | 301 / 0.77s |
| 新加坡2（高速下载、移动优化） | TLS 错误 / 约 5s | TLS 错误 / 约 5s | TLS 错误 / 约 5s | TLS 错误 / 约 5s |
| 美国洛杉矶-3 | 200 / 1.00s | 200 / 0.62s | 200 / 0.86s | 301 / 0.70s |
| 美国洛杉矶-1（联通优化） | 200 / 1.01s | 200 / 0.90s | 200 / 0.58s | 301 / 0.72s |
| 直连 | 超时 | 200 / 1.33s | 超时 | 超时 |

节点标签取自探测开始时的监听端口配置；运行任务可以自行轮换，严格复测还应逐请求记录控制器当时选择和实际连接链。该探测支持优先排查/临时隔离异常新加坡路径，不能认定节点永久失效、所有洛杉矶节点速度相同，或统一切换直连。首页 200/301 只证明当时 HTTP/TLS 可达，不证明验证、转换 API 和视频 CDN 均可用。

本次当前任务日志也出现多站点 `ERR_CONNECTION_CLOSED`、downmp3 `SSLEOFError`；部分 downmp3 请求约 5 秒失败，与上述路径异常相符。仅这些证据尚不能确定代理供应商、节点协议、上游网站中的具体故障位置。

**优先建议：** 为“节点 × 下载器/源站”建立健康记录。连续连接或 TLS 错误触发短期冷却，只允许少量恢复探测；实际视频任务不应持续消耗名额重试同一异常组合。既要测连通，也要按有效传输速度、失败率、重传量选择出口，保留有限探索，避免所有服务器同时挤向单个出口。当前每视频轮换不区分健康和吞吐，不能保证负载均衡收益。

### 2. 浏览器等待占用了大部分任务名额

第一段三个快照中，8 个任务分别有 4、5、3 个处于 `waiting_browser`；第二段通常有 4–5 个。部分任务累计浏览器等待约 250–300 秒，仍占用进程和任务租约。

例如任务 `de289a38...` 约 223 秒完成，其中实际下载约 73.7 秒。另一个任务 `0a47e05d...` 本轮约 355 秒后重新排队，累计等待浏览器约 291 秒，最终又遭遇 API 连接错误。前置等待期间不会产生视频传输。

当前 `web_worker.py:354` 的 `attempt()` 串行执行解析和传输；`webapp/browser_pool.py` 在工作进程内等待浏览器名额，默认等待上限 600 秒。Bergung/yt5s/yt1d 共用 2 个浏览器，网站验证或转换会长期占住这些资源。

**优先建议：** 改为有界流水线，独立控制解析、转换等待、文件传输、成品校验：

```mermaid
flowchart LR
  A[共享任务队列] --> B[本机解析池]
  B --> C[少量就绪下载地址]
  C --> D[独立文件传输池]
  D --> E[校验与幂等交付]
  R[资源与成功吞吐反馈] -.-> B
  R -.-> D
```

第一阶段可以先做实例内流水线，继续沿用现有任务租约与计费去重；不必一开始就在全局数据库存储和跨服务器派发签名下载地址。就绪队列仅预取有限数量，达到上限后停止解析；记录地址有效期和生成时出口，过期只重新解析，防止将绑定出口的地址换路径下载。等待上游转换尽量采用轻量轮询，不为每个等待任务长期保留一个完整下载进程。

### 3. 浏览器复用受到进程归属和节点轮换限制

`webapp/yt5s_browser.py:134` 按工作进程持有浏览器，会话空闲 5 秒关闭；代理节点变化、使用 20 次或存活 300 秒也触发回收。文件下载经常远超 5 秒，后续任务又每视频换节点，难以持续复用登录/验证会话与浏览器进程。

现有实现已经具备复用和共享浏览器容量保护，优化应在此基础上发展。可按代理出口维护少量可借用会话，把浏览器归属从下载进程转移到解析池；健康出口保持有限粘性，减少反复启动和验证。必须保留 resident 浏览器容量、内存预算、故障回收与会话隔离。单独延长空闲时间会使闲置浏览器继续占住共享名额，可能增加其他进程等待。

### 4. 普通 MP4 不能靠“分片并发”自动多连接提速

`webapp/downloader.py:68` 只设置 yt-dlp 的 `concurrent_fragment_downloads`，`:69` 的 10 MiB `http_chunk_size` 表示分块请求大小，两者不等价于对普通 MP4 建立多条并行 Range 连接。

本次代理连接采样中，一个 `dx22.videodownapi.com` 连接约 4.09 MB/s；第二段通常只有 1–2 个传输任务，与几十 Mbps 总吞吐相符。该样本不能用作源站或节点的普遍限速结论。若目标仍为 300 Mbps，按单连接 4 MB/s 举例，需要约 10 个同时有效传输的连接；正在等待浏览器的任务不能计入。

可增加可选的 HTTP 分段传输，但先以小 GET 验证正确的 `206`、`Content-Range`、长度及文件一致性；不能只检查 HEAD 的 `Accept-Ranges`。有些第三方地址不支持续传，10 月 26 日记录已出现 `Unable to resume`，本次未重新验证这些媒体地址的 Range 能力。不支持的源继续单连接，利用不同视频并发填充带宽。

如引入 aria2 或内部 Range 池，应按源站、节点和实例统一限制总连接数，先从单文件 2–4 条探索；失败、过期和服务器忽略 Range 时回退，保留 FFprobe 校验、原子完成与交付去重。避免“任务数 × 单文件连接数 × 服务器数”无约束增长。

### 5. 历史数据库/磁盘协调问题仍需覆盖，但不是这次采样的首要结论

业务库为 MySQL 5.7.44，8 次 SELECT 1 约 0.83–1.19 ms；现场 PROCESSLIST 主要是 Sleep，不能据此认定复杂领取事务也同样快速。实例间任务领取会锁同一 `fleet_budget` 行（`webapp/store.py:687`），且 5.7 不支持 `SKIP LOCKED`。实例较多时即使总下载带宽充足，也可能被集中领取锁与网络往返限制。

当前库的行锁等待、Slow_queries 数值为累计值，不能把全部累计等待归因于本次采样。两次快照间行锁等待累计从 8698 到 8701、累计等待时间约增加 429 ms，未显示本次持续严重锁堵塞。

历史日志在 10 月 29 日 00:18–00:44 出现工作进程因 `SchemaUpgradeInProgress` 退出，另有 MySQL 1205 锁超时。每个新工作进程都会构造 Database 并检查升级状态（`webapp/database.py:338`），多节点和频繁重建进程会放大启动竞争。建议部署阶段单次迁移，工作进程启动只验证兼容版本；运行中避免反复获取迁移锁和检查所有索引。

本地磁盘预算另外使用 SQLite，与业务 MySQL 分开。10 月 27 日历史记录有 `DiskCoordinationBusy` 和 `database is locked`；当前代码已将其归为可恢复资源等待并减少无变化写入。本次限定当前时段的日志抽样未捕获新的 `attempt_released` 或 `worker_crash` 事件，不能照搬旧诊断，把本地锁认定为现在的主要瓶颈。

后续仍应监控本地锁等待时长、目录扫描耗时和资源释放次数，保留原子空间预留，不通过关闭磁盘预算提高表面吞吐。

## 面向不同服务器的自适应方案

推荐增加“自动吞吐”模式，并保留手动上限及现有画质语义：

1. **识别真实资源额度。** CPU 综合 affinity/cpuset、cgroup CPU quota 和宿主机可用量；内存综合 cgroup 限额、容器用量和宿主机压力。不能因为容器看到宿主机 64 核就启动 64 核对应并发。网卡协商速率也不能充当公网带宽目标，带宽由部署配置或实际有效探测提供。
2. **分阶段确定容量。** 解析并发受浏览器 CPU/内存和服务端限流约束；HTTP 转换轮询受请求频率约束；传输并发受网络、磁盘与连接预算约束；校验合并独立限制。J4125 当前先以 2 个浏览器为基线，不宜在已有 CPU 高峰时直接扩大到 8 个浏览器。
3. **根据成功吞吐反馈调参。** 每 5 秒采集，每 30–60 秒评估；单次只改变一个阶段的小幅并发。资源压力低且增加名额带来稳定吞吐收益时逐步增长；429/5xx、超时、CPU 压力、磁盘等待或内存压力升高时退让。设置稳定窗口、冷却和迟滞，避免阶段性无任务被误判为网络容量不足。
4. **把资源供给和网络路径一起决策。** 记录 provider × node × source 的准备耗时、活跃传输速度、成功率、地址过期与重传。异常路径熔断后换健康组合，小文件/大文件采用不同样本统计；不能只拿延迟测速排名，也不能把第三方转换期间的零速度计入纯传输测速。
5. **保证质量可比。** 当前 best 在不同下载器含义不同，downmp3 最高请求档为 1080p。按用户允许的实际分辨率、帧率与音视频完整性约束选源，不能通过降低画质把“更快完成”冒充同等质量吞吐提升。短期速率用实际传输字节，最终目标用同质量成功视频数/小时及去重成功字节/小时共同判断。
6. **保留存储反压。** 就绪队列和在途文件必须受当前分类预算、剩余空间和文件大小预估约束。当前测试总预算 20 GiB、测试分类 16 GiB、低水位 10 GiB；正式保留成品还需要独立输出容量和后续归档吞吐管理。项目当前没有已实现的网盘上传链路，不能用下载测试成绩推断未来下载+上传总耗时。

强机器可以提高传输连接和无浏览器解析并发，弱机器可以保持较小解析池并让网络传输继续运行；两者不应统一使用 `CPU 核数 × 固定倍数` 作为最终容量。

## 多服务器扩展必须处理的上限

- **单实例 16 上限：** 调度器、设置校验、浏览器名额与代理监听槽均有 16 的假设。只放宽输入校验不会获得完整扩容能力。应将传输池、解析池、代理会话数解耦，再系统性调整限制。
- **全局 32 预算：** 当前 `fleet_budget=32`。即使部署 10 台、每台 8 个任务，集群仍最多允许 32 个在途下载任务。现在单机 8 个时尚未触顶。以后应区分实例资源额度、集群上游连接限额与业务公平性，按实际容量分配。
- **共享领取热点：** 短期保留正确的全局名额锁并监控 P95/P99；扩大节点数前评估 MySQL 8.4、`SKIP LOCKED`、实例名额租约及小批量领取，缩短全局锁内操作。数据库升级属于独立变更，需要验证备份恢复和迁移兼容。
- **共享出口：** 服务器增加但仍共享同一代理出口/供应商限额，吞吐不一定线性增长。按实际出口识别连接预算、带宽和限流，不按节点显示名称判断独立性。
- **统一可观测性：** 每台机器输出真实有效资源额度、阶段容量、运行/等待数量、网络接收、成功字节、重传、失败分类和调参原因；中心汇总成功吞吐及预计剩余工作量。

## 建议落地顺序与验收

**第一批：路径健康与有效并发。** 复测并隔离当前异常路径，加入 provider × node 冷却和受限恢复探测；补齐正在传输数量、等待浏览器时长、成功吞吐及重传的观测。使用固定且可比的质量目标测健康节点，不盲目把 downmp3 提到第一位。本次其 API 也有连接失败，且画质上限不同。

**第二批：任务流水线。** 将解析、转换和传输拆开，加入小容量地址预取队列和共享浏览器会话；以当前服务器的 2 浏览器为起点，提高“实际在传文件”的数量。资源允许时先做传输并发 4、6、8、12 的阶梯试验，16 只作为后续候选，不能视为预期最佳值。

**第三批：自动控制与集群额度。** 引入 cgroup 资源识别、阶段反馈调参和节点吞吐学习；同步改造单机 16、集群 32 的固定限制及任务领取热点。Range 多连接作为经过源站验证后的可选能力。

每组使用相同视频集合和质量约束，排除重复跳过，预热后至少运行 10–15 分钟，并做不同时间段重复对照。比较成功视频数/小时、成功字节/小时、网络吞吐、错误/重传、浏览器等待 P95、CPU/内存/磁盘压力和数据库领取延迟。合格条件是最终有效工作完成得更快，且错误、质量及账本一致性符合要求。

如仍以 300 Mbps 为目标，可先以接近线路可持续能力的 90% 左右作为传输阶段试验目标；上游持续供给不足时应明确报告瓶颈，不保证固定 270 Mbps 或固定倍数提升。CPU 无需为了“占满”而额外做无效解析或转码。
