## CPU 主要来源

在候选测试结束后、发布备份开始前，进行了进程级约 32 秒采样；未执行压力测试。以 100% 代表一个核心，主机四核的总容量为 400%。采样中下载进程合计平均约 116%，本地处理进程约 50%，Node 子进程约 16%，主应用约 17%，MySQL 约 11%。这些值仅代表该短窗口。

下载、处理和 Node 解析的高峰会叠加，局部半秒样本中下载进程合计超过 200%、本地处理超过 180%、Node 超过 130%；它们发生在不同样本，不能把这些峰值直接相加。Node 的父进程确认为下载工作进程，代码在该环境中选择 Node 作为 yt-dlp 的 JavaScript 运行时。FFmpeg 和 FFprobe 也有短时开销，数据库不是此次观测的主要 CPU 来源。

本地处理进程存在反复启动开销。最近约 15 分钟的保留日志去除重复采集事件后，记录 162 次处理进程启动，已配对的 161 个生命周期中位数约 2.11 秒。窗口包括此次应用切换，不能作为全天稳定启动率；正常队列实现也会在暂时无工作时退出，由监督器按需重建。隔离容器的一次冷启动测量：导入工作进程入口消耗约 0.62 秒 CPU，继续导入队列和本地处理模块约 0.43 秒 CPU。相比两秒左右的短生命周期，重复加载成本值得优化。

后续优先考虑让本地处理进程在短暂空闲时继续待命，减少重复初始化；再评估独立限制解析阶段的并发，保留下载传输能力与现有资源保护。此次仅发布账号间隔修复，CPU 调度策略未纳入该补丁。

诊断曾试用整棵进程树的调用栈采样，其自身开销明显，相关 CPU 百分比和包含等待线程的栈占比没有用于上述结论；后改用进程计时、pidstat 与低频单进程辅助采样。辅助 Python 栈样本较少，不能据此认定某个 Python 函数是主要热点。临时 profiler 可执行文件与下载包已删除，保留原始采样以便复核。
