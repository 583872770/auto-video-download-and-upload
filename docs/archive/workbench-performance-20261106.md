# 下载工作台性能优化（2026-11-06）

目标服务器：216.227.169.90，4 vCPU / 16 GiB，Docker + MySQL 8.4.13。
现场原因和原始基线见 `workbench-lag-diagnosis-20261106.md`。这是在该诊断之后执行的变更记录。

## 实现

1. MySQL：在线执行 `SET PERSIST innodb_buffer_pool_size=2147483648`，从 128 MiB 扩大至 2 GiB。没有修改事务持久性参数。Compose 同时加入可覆盖的 `MYSQL_INNODB_BUFFER_POOL_SIZE`，默认 2G；小内存机器需按可用内存调整。
2. 导入：每批从 2000 条缩为 500 条。查重的 video_id / URL 条件分别使用对应索引查询，保留行锁和原子导入游标，仅选择查重与恢复需要的字段。保留跨导入去重、清空取消和已移除任务恢复语义。
3. 调度：保留共享准入锁和任务租约校验；不再对已存在的调度资源反复执行空更新。过期许可证先通过普通查询取出，再按许可证主键删除，避免 DELETE 子查询锁住任务行。每个资源最多每 30 秒清理一批 256 条，额度计算仍只统计有效任务和所有者。
4. Redis：只存临时实时进度，不存队列、租约或完成账本。每个任务按数据库、所有者、开始时间和尝试次数隔离；缓存有效期 120 秒。同一阶段约每 5 秒写一次 MySQL，首次上报、阶段变化和任务结束立即写库。所有权和执行权限继续由 MySQL 校验。
5. 故障回退：Redis 连接/读写超时 200ms，异常后退避 5 秒并按原逻辑写 MySQL；恢复后比较进度时间戳，旧缓存不能覆盖故障期间写入的新进度。终态不读取运行缓存。

## 配置与部署

- 本地 MySQL Compose 增加内部 `redis:7.4-alpine`，内存上限 384 MiB，其中缓存最大 256 MiB，allkeys-lru，不开启持久化，不映射公网端口。
- 应用通过 `REDIS_URL=redis://redis:6379/0` 使用缓存。远程 MySQL Compose 默认留空，保持原有 SQL 进度逻辑，可自行接入 Redis。
- redis-py 固定版本 5.2.1；依赖锁和环境变量示例已更新。
- 本次服务器候选镜像 `youtube-downloader-local-app:performance-20261106`，从当前生产镜像构建，只覆盖本次三个既有源文件、新的缓存模块和依赖锁，保留已部署的其他功能。
- 原镜像保留为 `youtube-downloader-local-app:pre-performance-20261106`；容器替换时保留原环境、端口、数据卷、网络、健康检查和重启策略。

## 验证方法

- 本地相关 92 项测试通过；新增“批量导入恢复已完成但被移除的视频”测试单独通过。
- 隔离 MySQL 容器运行测试，创建并删除随机测试数据库，没有在生产库运行测试套件。
- 最终相关 MySQL 回归合计 43 项通过、1 项跳过（仅适用于 MySQL 5.7 的阻塞锁兼容测试）；最终任务套件 11 项全部通过。其他 Fleet 扩展测试 21 项通过，1 项既有类型断言失败，见下述说明。
- 新的并发回归：另一个连接持有任务行锁时，其他任务的准入及许可证清理需在 2 秒内完成。
- 修正旧 MySQL 队列测试的独立执行环境，补齐独立模式配置；修正死锁模拟回调的参数，以适配当前统计接口。
- 真实 Redis 联调：同一阶段连续 100 次进度上报只有 1 次进度 UPDATE，页面读取为最新值；故障写库、恢复旧缓存屏蔽、终态写入均验证通过。这是短时合成上报实验，不能换算成整个数据库或下载带宽提高 100 倍。
- 扩展 Fleet 测试中发现一个既有失败：MySQL 聚合的媒体数量由 JSON 编码为字符串，测试期望整数；使用优化前镜像复现同样失败。本次未修改该接口。

原始验证、部署脚本和采样保存在 `.runtime/cache-archive-20261111/validation/performance-20261106/`；服务器保存的 Docker 配置备份含运行环境，目录权限 0700、备份权限 0600，不应公开发布。

Redis 快照：26 个带过期时间的键，内存数据约 1.59 MiB，容器占用约 3.5 MiB，未发生缓存淘汰。应用和 MySQL 容器当时分别约占 1.91 GiB 和 2.75 GiB。
