# r46 带宽利用率分析

2026-11-17 19:07～19:09（北京时间）重新采样公网接口 ens18，并读取有效 Redis 进度、调度状态、近期成功任务及有限长度的任务日志。本次仅分析，没有调整线上配置或代码。

## 当前实测

120 秒公网接收平均 765.65 Mbps，窗口峰值 992.09 Mbps，最后约 30 秒加权平均 980.37 Mbps。CPU 平均忙碌 69.65%，I/O 等待平均 4.37%，最少可用内存 7.18 GiB。采样期间没有 queued 状态的后处理积压，但存在 3 个已经 failed 的遗留处理计划。

链路能接近满速；主要问题是任务流量不连续，使长期平均下降。不能把某一短时间的空档直接归因于服务器硬件性能不足。

## 主要原因：等待期间仍占有任务、账号和传输额度

`webapp/downloader.py` 在 sleep 预设开启时设置请求间隔 0.75 秒、文件启动前随机等待 10～20 秒。`webapp/parallel_http.py` 将同一文件启动范围应用于字幕。

`webapp/delivery/executor.py` 顺序获取封面、视频轨、音频轨、每种语言的字幕；`webapp/adapters/execution.py` 先取得传输许可并发布 downloading 阶段，再调用会执行 sleep 的下载器。因此下载中数量不能代表正在接收数据的数量。

有效实时进度的一次采样：28 个运行任务中，24 个标记 downloading，其中 13 个超过 5 秒没有新增字节；只有 10 个运行任务在最近 3 秒有新增字节。字节停顿也可能包含上游慢响应，不应全部算作主动 sleep。

近期成功任务的例子：`Fv--JW_BMl0` 执行约 62.7 秒，日志中的 sleep 合计约 48.7 秒。视频轨启动等待平均约 15.3 秒，音频轨约 14.8 秒，字幕请求约 14.9 秒。

## 多语言字幕放大等待

`caption_plan()` 的 original 模式收集所有符合来源条件的原始语言，不只选视频主要语言。

`em53rNvJfmo` 的日志确认单次来源尝试下载 75 种不同语言的人工字幕；执行 1325.8 秒，其中 sleep 合计 1143.29 秒。这个例子说明小体积字幕能够长时间占有来源任务与账号，但贡献很少带宽。

近期 60 个成功任务的整体执行中位数约 87.4 秒，累计 sleep 中位数约 62.7 秒。累计 sleep 读取任务保留日志，部分任务包含多次来源尝试；不能将全部任务的 sleep 合计与最后一次执行时长直接相除。75 语言例子单独验证了来源尝试次数。

## CPU 保护放大平均带宽波动

实测最近一次 CPU 临界保护记录为 99.9%，进程上限从 29 降为 23。代码在达到调整周期且 CPU 至少 97% 时可以缩容 20%，恢复则要求 CPU、I/O、内存达到条件，每 60 秒只增加 1 个进程。从 23 恢复到 29 至少需要约 6 分钟。

采样中 CPU 使用主要可见于下载 Python 进程；尚未进行函数堆栈性能剖析，不能将其全部归因于解析、JS、启动或具体一条代码。应先定位峰值来源，再优化保护策略；不建议关闭保护。

## 连接预算的静态分配

服务器配置分片并发 8、总下载连接预算 51；当前传输容量为 29。`fragment_connection_budget()` 按容量平均分配，整数除法 `51 // 29 = 1`，实际单任务分片预算为 1。近期 60 个任务日志未出现 HTTP 分块并行启用记录，与预算一致。

仅少量任务真正传输时，剩余连接不会自动借给大文件。这是可优化的调度方式，但单连接任务也曾达到数百 Mbps，不能断言它是唯一限速原因。增大并发还可能增加 CPU 与源站请求压力。

账号配置为：每账号任务启动间隔 55 秒、任务结束休息 10 秒、全池任务启动间隔 0 秒、每账号并发 1。不是整个服务器每 55 秒才启动一个任务。当前同一任务的串行等待已很明显，不能仅靠降低 55 秒解决。

## 新发现的交接缺陷

3 个任务在字幕报“字幕请求未生成可用文件”后，父任务被置为 failed，已经落盘的画面与音轨仍存在，处理计划的 attempts 为 0、resume_network 为 true。因为本地 claim 只领取 queued 父任务，已保存的轨道没有被后处理接手。

涉及视频：`2SIlYfGUv-I`、`QOZNmBg4omk`、`a5kI66UnZDc`。

原因链为来源异常保存处理计划后继续抛出，通用任务失败结算没有优先完成本地交接。这是需要优先修正的正确性问题，不是当前全机带宽的主要限制。

## 建议顺序

1. 修复字幕失败时已有轨道的交接，处理完成后只补缺项。
2. 明确任务字幕语言范围：视频主要语言、指定语言、全部可用原始语言；不要用含糊的“原始字幕”隐含选择所有语言。
3. 把文件启动等待纳入统一延迟调度，避免等待持有传输额度，并解决整个任务长期占有账号的问题；视频与字幕继续遵守同一套账号并发、间隔和冷却规则。
4. 针对 CPU 峰值做性能剖析，减少集中启动与重复初始化，再改善缩容和恢复，保留持续高负载保护。
5. 在总连接预算内按真实传输需求动态分配连接，优先给大文件闲置连接，收回时保持公平性。
