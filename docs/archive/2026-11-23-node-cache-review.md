# 洛杉矶 Node 重复计算、缓存与解析并发排查

本轮只检查洛杉矶 `216.227.169.90`。没有修改应用代码、配置或账号，没有暂停、重启或发布服务；仅在临时目录和隔离容器中做实验。运行版本为 `youtube-downloader-app:download-efficiency-20261123-r62`，yt-dlp `2026.11.15.232800`、Node `v22.23.4`，没有 Deno。线上观察与隔离实验分时执行，不将实验期间的 CPU 当作自然业务占用。

## 已确认的原因

当前存在明显的跨任务重复准备工作：相同版本的公共播放器 JavaScript 被不同视频重新获取、解析和预处理。已检查的 43 份任务日志中，42 份含播放器/求解记录，全部为 `6b3d0364-main`；每份都是一次播放器请求和一次 Node 求解。

这不等于单个视频的音频、视频、字幕各自重复启动 Node。项目一次获取视频信息后再选择轨道并下载；此次按进程映射到 47 个任务的 47 个 `node -` 求解进程，每个任务均只观察到一个。另观察到 2 个非常短的其他 Node 进程，未采集完整命令，不将它们计为重复求解。采样可能漏掉极短进程，不能据此断言其他时段绝无任务内重试。

对应源码路径：

1. `webapp/downloader.py:build_ydl_options()` 明确设置 `cachedir=False`。
2. `webapp/delivery/executor.py:acquire()` 每个视频尝试都构造新的 `DeliveryDownloader`。因此 yt-dlp `YoutubeIE._code_cache`、`_player_cache` 等对象内存缓存不能自然跨视频保留，即使 Python 工作进程自身继续运行。
3. 当前 yt-dlp 的 `YoutubeIE._load_player()` 只在本提取器 `_code_cache` 中缓存播放器源码；给普通 `cachedir` 设置目录不会自动把这个源码缓存改成共享磁盘缓存。
4. `EJSBaseJCP._ENABLE_PREPROCESSED_PLAYER_CACHE=False`。官方源码注释说明，预处理结果体积大，尚未实现轮换。每次 Node 因此仍收到原播放器源码，重新构建语法树、查找求解函数并生成可执行代码。
5. `NodeJCP._run_js_runtime()` 每批求解启动一个 `node -` 子进程，通过 stdin 传入库、求解器、播放器及挑战输入，结束后退出；没有跨任务常驻的 Node 进程池。

yt-dlp 已在一次提取内部批量处理 n / signature 挑战，部分重复输入在本提取器内去重、缓存。因此优化重点应先放在跨任务的公共播放器准备，避免重复实现已有的单次提取批处理。

## 当前并发策略

当前读取到 `download_task_limit=0`、账号池 33 个、每账号会话上限 1、账号池任务启动间隔 0；正常工作进程容量随后快照为 31，实际动态上限受资源保护在 23–29 间变化。这些值与上一次发布采样时的 20 个任务上限不同。本轮没有修改它们。

`RequestScheduler.permit('resolve')` 已包围 `extract_info()`，但其申请为 `('source-resolve:<instance>', None, 1)`，`None` 表示没有数字容量上限。这个许可仍检查任务租约、账号及源站冷却，却没有独立限制同时解析数量。`DownloadStartGate` 在账号准入完成后就释放；当前启动间隔为 0，也不覆盖后续的 Node 计算。因此整体任务数和原有 CPU 反馈构成间接约束，不能保证某个瞬间只会有 1 或 2 个求解器。

当前并非几十个 Node 持续一起运行，最大观察值为 3，达到 3 的时间很少。降低全部下载任务数量会同时减少正常网络传输，证据不足以支持把它作为首选方案。

## 隔离复用实验

在线采样完成后，额外获取一次同版本公开播放器脚本，不携带业务账号或 Cookie。URL 为 `https://www.youtube.com/s/player/6b3d0364/player_ias.vflset/en_US/base.js`，大小 3,060,278 字节，SHA-256 为 `b7ae7cd9ebe2c512f481f2e13e8a09d4899fbbb9495ffc411bf4babdb4984c75`。

使用正在运行的不可变镜像启动临时容器，网络禁用、CPU 限制 0.5 核、内存限制 512 MiB、进程上限 64，不挂载业务目录，不注入业务连接或凭据。只读挂载上述公共脚本及实验代码。每轮都新建下载器和 Node provider，通过当前版本真实的 Node 求解路径处理两条合成 n 输入及一条合成签名输入；不向真实媒体发送下载请求。

三个方案各运行三次，交错执行；预处理方案另有一次冷启动预热。修改仅作用于实验子类的 provider 标志，未改第三方安装文件或业务实现。

| 模式 | Node CPU 秒中位数 | Python 父进程 CPU 秒中位数 | 墙钟秒中位数 |
| --- | ---: | ---: | ---: |
| 当前方式：缓存关闭、每次处理原播放器 | 2.655 | 0.080 | 5.478 |
| 仅打开普通磁盘缓存 | 2.551 | 0.077 | 5.282 |
| 复用播放器预处理结果，仍新建 Node | 0.382 | 0.088 | 0.971 |

普通磁盘缓存没有改变原播放器预处理路径；小幅时间差不能视为稳定收益。复用预处理结果后，该段 Node CPU 约减少 85.6%。十次运行的结果摘要一致，所有请求返回成功、结果哈希相同；但只有同一播放器版本和合成输入，尚不替代多版本、真实格式和取消/恢复回归，也不是整机或实际下载速度前后对照。

实验预处理缓存约 4,417,733 字节，比原始播放器更大，验证了上游关于体积和轮换的顾虑。预处理命中仍启动一次 Node，只跳过公共脚本的重复预处理，保留各任务自己的挑战求解。

另通过当前版本真实的跨下载器缓存接口验证：相同播放器与签名长度的 `sigfuncs` 可随普通磁盘缓存复用；`n` 结果当前只写对象内存缓存，新的下载器读不到它。本轮没有采集线上挑战明文或哈希，不能给出不同视频 n 输入相同的比例，也没有据此主张共享整个视频解析结果。

## 建议实现顺序

**第一步：建立当前实例有配额的公共播放器缓存，优先复用预处理结果。** 项目适配已固定的 yt-dlp / EJS provider，缓存键包含播放器完整版本/变体、yt-dlp 与 EJS 版本及运行时兼容标识；原始公开脚本也可按相同版本共享，减少重复 HTTP 获取。视频信息、临时媒体 URL、Cookie、PO Token、访问权限和各视频挑战仍按任务正常获取和验证。保持每任务独立下载器，避免账号会话或代理配置串用。

使用实例本地文件缓存，计入已有“运行缓存”预算，建议先给播放器原始及预处理缓存共 128 MiB 上限、最多 16 个版本、24 小时过期；最终参数以多版本实测调整。命中更新访问记录，超额或磁盘压力时自动淘汰冷条目；源码与预处理体积都算在同一配额，不能无限累积。业务维护与测试工作目录清理不能误删正在写入/读取的缓存。

同一个播放器首次未命中时，用按键的跨进程文件锁让一个进程建立缓存，其他进程等待后复读；不在网络或 Node 执行期间持有 MySQL 事务。原子写入，校验缓存结构和版本。损坏、过期或求解异常时删除该条目，至多回退原路径重建一次；真正的解析、权限或源站错误继续向上报告，不因缓存而吞掉失败。不建议直接打开上游隐藏标志后就上线，因为它没有容量轮换机制。

**第二步：给 Node 计算加独立、实例范围的上限，初始候选为 2。** 将等待放在真正的 JS 求解入口，继续保留任务租约、停止响应和账号/源站限制。等待不占数据库事务，不把 HTTP 等待或整段视频下载锁在这个计算名额中；工作进程退出后名额必须自动释放。已有 `source-resolve` 更适合描述整段解析，不能把它盲目设成 2 后长期占着等待网页或 API。

2 是后续验证起点，不是已经证明的最优值：四核上观察到最大同时 3 个、同时 2 个以上只占约 7.4%，缓存先减轻单次开销，再限制少数重叠高峰，预期比削减所有下载任务更有针对性。需要比较上限 1 与 2 的 JS 排队时间、解析 P95、媒体接收速率、CPU 峰值及账号开始等待，才能决定最终值；资源保护也可在持续 CPU 压力下暂时降为 1。

**暂缓做常驻 Node 池和整视频结果共享。** 当前 provider 是一次 stdin、一次退出的协议；常驻需要新增消息边界、超时、取消、版本切换、上下文和内存回收管理。隔离实验表明，在仍新建 Node 的情况下复用预处理已能消除大部分该段开销，先做它更容易验证。其他运行时或 V8 参数没有做对照，不据此建议直接切换。
