# 洛杉矶下载工作进程 CPU 调用栈诊断

本轮只连接洛杉矶 `216.227.169.90`，承接同日的[整机 CPU 诊断](2026-11-23-los-angeles-cpu-review.md)。没有修改项目实现、运行配置、数据库结构或已运行镜像，没有暂停或重启应用。临时采样与隔离实验文件保存在 `/tmp/frameflow-worker-profile-20261123`，取回证据后清理；本地原始材料位于 `.runtime/la-worker-profile-20261123/`。

后续已设置 `progress_delta=1` 并发布 r62，实施与业务采样结果见[下载进度、留样查询与性能验证](2026-11-23-download-efficiency-deployment.md)。下文的分析与隔离实验均针对改动前版本。

## 结论

下载工作进程存在一项明确可减少的开销：yt-dlp 原生分片下载在处理数据时反复生成终端进度文字，调用链为：

```text
FragmentFD 分片进度
  → FileDownloader._hook_progress
  → FileDownloader.report_progress
  → FileDownloader._report_progress_status
  → YoutubeDL.evaluate_outtmpl / prepare_outtmpl
  → 字段遍历、格式转换及终端打印
```

项目网页另用 `DownloadProgress.hook` 和 `DownloadMeter.hook` 接收结构化数值，`DownloadProgress.save` 已有 2.5 秒上报间隔。但该限频发生在应用自己的回调里，不能减少此前 yt-dlp 已完成的终端文字格式化。原生分片还在内部 `HttpQuietDownloader` 与外层 `FragmentFD` 分别处理进度，同一传输有重复的文字计算机会。

当前版本的 `noprogress=True` 仅把打印器换成静默打印器；`report_progress` 的格式化与两次 `evaluate_outtmpl` 仍执行。因此只关闭输出并不能解决本次热点。

普通 HTTP Range 路径的持锁样本主要来自请求、响应读取和缓冲处理，终端格式化占比低得多；不能把原生分片的结论推广为所有下载路径均有相同比例收益。

## 在线采样与有效性

版本保持 `youtube-downloader-app:realtime-data-fix-20261122-r61`。选取实际 CPU 和写入速率较高的下载/regular 进程，针对单进程采样，不递归采集整棵子进程树，也不读取局部变量、Cookie 或请求内容。

采用 `py-spy 0.4.1`，两轮有效采样分别为每秒 7 次、持续 75 秒，以及每秒 13 次、持续 90 秒，均使用 `--gil --nonblocking --threads --full-filenames`。计入监测与收尾的实际窗口约 79.18 秒和 95.26 秒。持锁样本用于找 Python 路径，不能完整刻画释放 GIL 的 TLS、系统调用及原生库 CPU。

| 窗口 / 主机 PID | 路径特征 | 有效持锁样本 | 终端进度链样本 | 占该进程持锁样本 |
| --- | --- | ---: | ---: | ---: |
| 第一轮 / 3415310 | yt-dlp 原生分片 | 77 | 32 | 41.6% |
| 第一轮 / 3416542 | yt-dlp 原生分片 | 49 | 23 | 46.9% |
| 第三轮 / 3407829 | yt-dlp 原生分片 | 201 | 89 | 44.3% |
| 第三轮 / 3425767 | yt-dlp 原生分片 | 186 | 84 | 45.2% |
| 第一轮 / 3421429 | 项目 HTTP Range，后续有解析 | 21 | 0 | 0% |
| 第三轮 / 3429179 | 项目 HTTP Range | 50 | 1 | 2.0% |

四个原生分片样本合计 513，终端进度链 228，约 44.4%。这是所选工作进程的 Python 持锁样本比例，**不能解释为整机 CPU 可以下降 44.4%，也不能解释为全部下载进程 CPU 的精确占比**。网络阶段和视频会切换，各进程 CPU、速度与解析活动不固定；不把选取前的短窗口 CPU 当作整个采样期间的 CPU。

第三轮中两个原生分片工作进程的同期 CPU 均值约为单核 12.25%、13.06%，平均写入约 7.41、8.65 MiB/s；Range 样本约为单核 8.04%、写入 8.67 MiB/s。这是不同任务的观测，不能作传输协议效率对照。

有效轮次中 py-spy 合计开销约为单核 0.38%、0.78%；只读进程监测脚本另约为单核 5.39%、5.75%。中间另试了一轮 `perf cpu-clock` 原生采样，但该内核上 perf 自身约占单核 123%，明显干扰整机。该轮约一分钟后结束，**整轮占用和原生样本均排除出性能结论**。其中非持锁 Python 样本包含大量 SSL 读取、线程池和日志管道等待，同样不作为 CPU 时间比例。随后重新完成上述第三轮低开销持锁采样。

任务数据库更新与磁盘预算也被采到，但第三轮两个原生分片进程中，任务数据库调用链各仅 3、2 个持锁样本，磁盘预算各 5 个。没有证据将它们列为本次下载进程的第一热点；其中数据库服务端的扫描问题仍是前一份报告确认的独立问题，不能混为下载进程 CPU。

## 隔离比较

使用服务器正在运行的同一不可变镜像启动临时容器，不挂载业务卷、不注入连接与账号配置，`--network none`，CPU 限制 0.25 核，内存限制 256/384 MiB。测试仅在容器内部使用合成进度事件或回环 HTTP，不访问真实上游。

第一组向真实 `FileDownloader._hook_progress` 连续传入 1000 条合成进度事件，每种设置重复三次。结构化回调每次均收到 1000 次。CPU 时间中位数：

| 设置 | CPU 秒 / 1000 事件 |
| --- | ---: |
| 当前默认行为 | 0.31990 |
| 仅 `noprogress=True` | 0.34037 |
| `progress_delta=1` | 0.00254 |
| 实验性仅跳过 downloading 文字方法 | 0.00114 |

这是高密度事件下对格式化路径的隔离测量，不包含正常网络时间，不能当作完整下载的提速倍数。实验性跳过仅存在于临时测试子类，没有修改项目或第三方安装文件。

第二组使用真实 `HlsFD` 下载容器内 HTTP 服务提供的同一份文件：64 个 64 KiB 分片，共 4 MiB，4 路并发，三次重复。两组均设置 `noprogress=True`，第二组再增加 `progress_delta=1`，因此差异来自格式化频率而非打印是否可见。

| 设置 | 三次 CPU 秒 | CPU 秒中位数 |
| --- | --- | ---: |
| 现有格式化频率 | 1.03160、1.06274、1.00669 | 1.03160 |
| 增加 `progress_delta=1` | 0.52749、0.46554、0.45706 | 0.46554 |

CPU 时间中位数约减少 54.9%。六次输出均为 4,194,304 字节，SHA256 与按顺序拼接的原始分片一致；每次都有 513 次结构化回调，最终事件均为 `finished` 且字节数一致。局部 HTTP fixture 包含服务器线程 CPU，是合成分片文件而非真实视频解码验证。真实 CDN 延迟、分片大小、HTTP Range、解析、转码和任务管理开销均不同，不能据此承诺线上整体降幅。

## 优化方案与顺序

1. **下载工作进程优先采用 yt-dlp 官方 `progress_delta=1` 控制终端文字进度。** 从 `webapp/downloader.py` 的参数构建入口设置，使交付下载及原生分片内部下载器继承；可同时静默重复进度输出，但不能仅设置 `noprogress`。结构化 `progress_hooks`、下载字节计数、速度采样、完成回执、错误与警告继续保留。`progress_delta` 位于 `report_progress` 方法内部，提前返回后 `_hook_progress` 仍会继续调用其他回调，已由两组隔离实验验证。
2. **与之前的留样查询索引修复分别实施和量化。** 前者减少下载进程的重复格式化，后者减少 MySQL 扫描；两个问题分别有证据，都比直接削减全部下载并发更优先。上线时最好分步观察，避免无法区分收益来源。
3. **剩余原生分片开销暂不重写。** HTTP 请求准备、URL 处理、TLS、分片文件及缓冲仍有实际成本。需要改变网络引擎、分片存储或连接策略时，再针对该路径做独立对照；本次证据不支持承诺它们的具体可节省比例。
4. **状态读与资源监控列为后续精简项。** 不移除租约、所有权、停止、磁盘监控和账号保护。当前采样未证明这些是下载进程首要 CPU 热点。

实施验证应覆盖 HTTP Range、HLS/DASH 原生分片、音视频顺序、字幕、阶段切换、最终完成、取消与重试；既要检查网页进度和错误记录，也要核对文件哈希与字节统计。官方 `progress_delta` 对阶段内文字有限频，但 finished 等边界事件仍处理，且不同内部下载器各有计时器，不保证终端总输出严格每秒一条。

上线后在无采样工具、构建或备份干扰的窗口，比较每 GiB CPU 秒、媒体接收量、完成数量及失败类型；不能只比较某一瞬间 CPU 是否到 100%。本轮没有发布任何变更或做线上前后对照。

## 收尾

最终应用仍为原 r61 镜像，健康、重启次数 0、无 OOM；实例未暂停、无停止请求、错误为空，快照有 19 条运行任务。下载器、Range 下载、进度、磁盘预算及任务租约代码 SHA256 与本地文件再次核对。py-spy、perf 及临时测试容器均已结束；证据取回后删除远端临时诊断目录，不保留新增服务或依赖安装。
