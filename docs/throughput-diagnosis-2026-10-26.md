# 300 Mbps 下载吞吐现场诊断

时间：2026-10-26，约 22:21–22:30（北京时间）。对象：当前运行的 `youtube-downloader-app-1`。通过 SSH 读取系统、容器、当前任务、日志和代理现有连接，并对三个当前下载地址发起 HEAD 请求。没有修改服务器配置、数据库业务数据、下载策略，也没有重启或停止任务。未进行会竞争下载带宽的大文件测速。

## 实测与结论边界

300 Mbps 对应理论 37.5 MB/s，实际可用吞吐还受协议开销和线路影响。20 秒分段采样得到：

| 4 秒采样段 | 宿主机接收 Mbps | 下载容器接收 Mbps |
|---|---:|---:|
| 1 | 114.19 | 111.18 |
| 2 | 135.77 | 131.42 |
| 3 | 94.38 | 91.72 |
| 4 | 107.63 | 104.58 |
| 5 | 133.27 | 129.11 |

这段时间主要接收流量来自下载容器，约 11.5–16.4 MB/s。它说明现场确实未吃满 300 Mbps，不代表长期峰值或宽带本身的最高能力。尚未做同文件、同节点的对照吞吐测试，不能仅凭这些数据区分源站限速与代理线路瓶颈。

## 当前实际配置

- 下载进程：12；yt5s 浏览器：2；分片并发：8。
- 下载器顺序：downmp3 → yt5s；测试模式；所有下载经 Clash/Mihomo。
- 开启每个视频轮换节点，候选包含洛杉矶、凤凰城、新加坡等线路。
- 临时文件总预算 20 GiB，测试文件分类预算 16 GiB；剩余空间低水位 10 GiB、恢复 15 GiB。

配置及实例运行记录已交叉核对。本次没有调整上述数值。

## 影响吞吐的已确认因素

### 1. 主下载方式是普通 HTTPS 文件传输，分片并发参数没有预期收益

当前主要传输源为 downmp3 的 `*.savenow.to`，回退 yt5s 使用 `videodownapi.com` 等地址。媒体元数据协议为 `https`、格式为 MP4，并非原生分片清单。`webapp/downloader.py` 的 `concurrent_fragment_downloads` 不会自动为普通文件创建 8 条并行连接。

任务记录中的单任务速度多在约 0.6–2.7 MB/s，部分明显更低。现有代理连接的 5 秒增量样本包括：

| 下载源 | 代理节点 | 接收 MB/s |
|---|---|---:|
| videodownapi | 新加坡 1 | 0.033 |
| isabella91.savenow.to | 洛杉矶 1 | 3.015 |
| isabella91.savenow.to | 洛杉矶 2 | 1.065 |
| penny83.savenow.to | 新加坡 2 | 2.684 |
| nora82.savenow.to | 新加坡 2 | 0.615 |

这是不同连接和时刻的样本，不能直接据此给节点做可靠排名；源站、文件与连接条件也不同。可以确认当前实际传输速度不均，节点名称中的“高速下载”不构成吞吐保证。

### 2. 中断后的无法续传导致重复传输

日志已确认：

- 任务 `8c57d40a9071425b9746a75f892a7184`：传输约 619.77 MiB 后读取失败，自动重试并出现 `Unable to resume`。
- 任务 `0f96cd2a7d064b91be25f4acdd99207c`：约 77.61 MiB 后出现相同情况。
- 一个 yt5s 任务出现响应未读完重试，且此前长期维持几十 KiB/s 的低速。

yt-dlp 在服务端未正确响应所请求的 Content-Range 时会重新写整个文件，以保证成品正确。这会重复消耗带宽和任务名额；业务大小仍应只登记最终完整文件，不能把重传量算成成功大小。

对三个当前 downmp3 地址的代理 HEAD 请求均返回 video/mp4，但没有 Content-Length、Accept-Ranges。HEAD 信息本身不能证明 GET 一定不支持 Range；结合上述实际续传失败，可以确认至少这些失败连接没有成功续传。多连接分段方案必须先验证 GET 返回正确的 206 和 Content-Range，不能直接对所有地址启用 aria2 或并行 Range。

同批直连 HEAD 中两个失败，另一个返回 0 长度、非 video/mp4 的响应。当前探测不支持把正式文件传输统一改成直连；仍需单独验证网络路径、请求响应和地址可能存在的出口限制。

### 3. 解析和转换占用下载进程

downmp3 任务通常先经历约 15–30 秒远端转换，再加上 API 请求与其他准备阶段；小文件样本总耗时约 52–79 秒，其中实际下载约 21–39 秒。准备等待不能产生持续视频传输，却占用下载进程。

两次运行任务快照中都存在约 12 个传输任务，说明本次不是单纯“没有领满任务”；准备时间主要解释任务交替时的吞吐波动。慢速 yt5s 长连接同样会长期占据名额。

### 4. 本机磁盘协调 SQLite 存在锁冲突，需要优先修复

现场最近 3 个失败任务的错误均为 `database is locked`，时间约 22:21:14–22:21:18。日志明确指向：

`webapp/disk_budget.py` → `connect()` → `BEGIN IMMEDIATE`。

它不是业务 MySQL 的连接故障。MySQL 的两批 SELECT 1 延迟约 0.7–1.1 毫秒。本机协调 SQLite 采用 DELETE 日志模式和 FULL 同步；多个进程及监控线程重复申请写事务，即使水位、预留、子进程列表没有变化，也会重复写入。

还观察到监控线程在 `track_children()` 中因相同异常退出。线程异常未分类成磁盘资源等待，而主执行中的同类异常被当成下载失败。这既影响调度稳定性，也违背“资源条件不污染下载成功率”的设计目标。

两批最新任务记录中各有 12 个 queued/disk_wait 条目，说明磁盘准入曾经介入；采样时磁盘仍余约 41 GiB。这与分类预算、预留量是不同维度，不能只看硬盘空闲空间判断是否能再加任务。等待记录不等于整个实例始终被阻塞。

## 硬件与系统情况

- 4 核、约 7.5 GiB 内存；同机有多个其他服务。
- 下载容器一刻约占 1.6 核、1.64 GiB 内存；随后 vmstat 采样 CPU 空闲约 60%–75%，没有持续 swap 读写。
- 网卡 1000 Mb/s 全双工，接收错误和丢弃计数为 0，未发现本机网卡协商为百兆的情况。
- 128 GB SSD，文件系统约余 41 GiB。采样大部分磁盘利用率约 15%–24%，有一次写入突发约 85%；存在频繁 flush 和 I/O 压力，不能说磁盘完全无影响，但没有证据表明它始终处于吞吐饱和。
- 容器没有显式 CPU 配额和内存硬上限。

这些采样未显示 CPU、内存或网卡链路是持续首要瓶颈；不能据此保证所有时刻硬件都有余量。未验证路由器、运营商、代理供应商实际提供的持续下载能力。

## 建议执行顺序

1. 修复本机磁盘协调：减少无变化写入和监控重复事务；缩短写锁持有时间；锁超时归类为可恢复的资源等待；监控异常必须回传主执行。继续保留原子空间预留、完成凭据和统计保护，不通过关闭磁盘预算提速。修复前不建议继续提高并发。
2. 增加按节点、下载源、阶段的实际吞吐和重传观测，用同一批文件、相近时段比较节点。稳定性和持续速度共同决定选择，不用延迟测试替代吞吐测试。
3. 将 API 解析/转换与文件传输拆成有界队列，提前准备少量地址；控制地址有效期、上游请求频率和浏览器数量。慢速兜底下载独立限制占用，避免阻塞主传输名额。
4. 验证具体源的 Range 能力。仅在正确支持 206、Content-Range、文件一致性和最终校验时引入受限的单文件多连接；不支持续传的源优先优化线路、降低断连与重下。
5. 完成以上工作后，在同样磁盘预算下比较 12 与 16 个传输名额，观察 5–10 分钟平均速率、失败/重传、磁盘等待与资源用量。16 是试验上限，不是跑满 300 Mbps 的保证。

本次只完成诊断，没有部署上述改动、调整统计或重试历史失败任务。现场结果支持“源站/代理链路与当前单连接方式为主要优化方向，另有必须修复的本地锁冲突”；尚不足以把剩余带宽缺口全部归因于某一个外部服务。
