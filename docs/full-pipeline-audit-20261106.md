# 下载系统全链路排查（2026-11-06）

本轮结论：线上目前没有持续锁表、Redis 故障或内存耗尽的证据。仍有值得处理的前端刷新和长期查询成本问题；大文件会产生磁盘写入突发。下一轮优化应优先减少本地重复工作，保留现有 Cookie 冷却、启动间隔和下载请求休眠。

本轮仅执行诊断读取和有界采样，未修改业务代码、线上配置、数据库索引、下载并发或 Cookie 状态；未额外向 YouTube 发起验证、解析或下载。报告和诊断脚本是本轮新增文件。

## 观察范围与证据边界

- 服务器：洛杉矶当前 Docker 部署；应用、MySQL、Redis 三个容器。
- MySQL 差分窗口：北京时间 **15:24:09—15:27:12**，约 182.8 秒；19 次锁状态采样。
- 页面接口：主观察 82 次请求，补充 20 次请求，合计 **102 次，全部 HTTP 200**。这是服务器本机访问应用的耗时，不包含用户浏览器到洛杉矶的网络延迟及浏览器渲染时间。
- 任务阶段：19 次运行中快照；初次读取最近半小时完成任务 140 条，未触及 600 条上限。
- 当前 r2 版本日志：从启动时刻 15:12:26 起过滤到约 15:27:18，按结构化事件内容去重；83 次 Cookie 准入、76 次结束。读取范围为近期完成任务、运行中任务和实例日志，日志有截断和保留上限，不是永久完整历史。
- 补充读取最近 200 份测试成品对应的大小和任务阶段耗时。这组样本包含更早运行记录，不能全部归为当前版本。
- 检查临时文件、日志目录、磁盘预算租约、容器 cgroup 和代码调用路径。未对两百万任务执行全表精确计数或压力测试。
- 当前实际存储模式是 **test**，下载后合并、校验、登记并删除。OSS 上传、素材库持续写入、大批量导入、浏览器渠道和字幕补下载没有活跃业务样本，只有代码审查，不能把这些路径称为已完成生产性能验证。

忽略目录中的原始证据：`.runtime/cache-archive-20261111/validation/full-audit-20261106/`。主要文件为 `host-results.jsonl`、`app-results.jsonl`、`http-results.jsonl`、`process-results.jsonl`、`detail-results.jsonl`、`http-extra-results.jsonl`、`extra-results.jsonl`、`digest-delta.json`、`stale-permits-final.json`。

## 线上现状

### 数据库：有短暂争用，未见持续阻塞

- 19 次采样的行锁等待边数均为 0；不能据此声称采样间隙完全没有锁等待。
- 窗口累计行锁等待增加 **28 次、723 毫秒**；无 SQL digest 错误增量、无磁盘临时表增量、无 redo 日志等待增量。
- COMMIT **8,036 次**，约 **44 次/秒**，语句平均耗时 **3.26 毫秒**。不同事务的累计耗时不能直接当作主线程阻塞时长。
- 缓冲池物理读取仅 **16 次／约 26 万字节**，逻辑读取约 188 万次。目前没有继续扩大 buffer pool 的实测理由。
- 8,019 次 ROLLBACK 包含 SQLAlchemy 连接结束时的正常事务回收，不能把这个数字当作业务失败数。
- 连接中止增加 1 次、连接建立增加 80 次；包含诊断工具的短连接，目前不足以归因为连接池故障，宜补充按进程连接错误统计。
- 数据库表行数估算与约两百万任务的业务计数差距明显。`information_schema.TABLE_ROWS` 和 EXPLAIN 都是估算，不能用作精确库存；批量导入后的统计信息值得另择窗口核查。本轮没有运行 ANALYZE TABLE。

### Redis：正在生效，当前不是瓶颈

- 窗口 GET 命中 **1,591 次**，未命中 **23 次**，原始命中率约 **98.57%**。
- 无淘汰、拒绝连接或错误回复；最终使用内存约 **1.27 MiB**，远低于 256 MiB 上限。
- Redis GET 累计服务器执行平均约 **4.47 微秒**，不包含客户端网络往返。
- 命中不等于业务必定采用缓存：应用还会检查任务尝试标识、租约和进度时间，当前没有对“命中但被拒绝”的原因计数。

### 主机与临时文件

- 三个容器均健康，重启次数 0，没有 OOM；应用无 CPU 配额节流记录。
- 18 个约 10 秒主机区间中，CPU idle **22.14%—77.49%**、iowait **1.57%—13.65%**；存在资源突发，未见整个窗口持续满载。
- 可用内存最低约 **9.29 GiB**；磁盘剩余约 **168 GiB**，使用率 13%。
- 补充以 root 读取进程计数，见到一个 Python 进程在约 10 秒内产生约 **2.42 GiB** 磁盘写入计数。该计数不能直接区分下载、合并、复制，也不等于写满物理磁盘；短命 ffmpeg 可能在两个采样点之间退出而未被捕获。
- 日志约 28.3 MiB；测试下载目录瞬时约 3.71 GiB，未发现超过一小时未更新的测试文件。运行中大文件会变化，不能据此认定所有临时目录都没有孤儿文件。
- runtime/cache 只有 24 个空目录，导入目录为空；浏览器目录当时不存在或不可读取，不能解释为浏览器业务健康验证。
- 当前日志目录有界扫描约 16 毫秒，磁盘接口最大 38 毫秒；日志清理目前没有成为持续热点的证据。
- 补充检查当时的 **76 条下载许可资源明细**，按任务状态、owner 和租约判断，过期／失配明细为 **0**。这是单点快照，不代表历史上从未有过期许可。首次补充脚本的最后一项遇到 Decimal 序列化错误，已单独重取该项；其他结果不受影响。

## 优化项与实施次序

| 顺序 | 位置 | 证据和问题 | 建议及收益边界 |
| --- | --- | --- | --- |
| 1 | 前端统一请求与轮询 | `static/app.js` 的通用 `api()` 没有默认超时；工作台和主刷新虽防重入，但悬挂请求可能一直占用防重入标志。主刷新 `Promise.allSettled` 等全部完成后才应用结果。 | 给只读轮询增加超时、取消和有界退避；各块成功即更新，显示数据更新时间。写操作超时必须提示结果待确认，不能自动重复提交。能改善断网／慢请求时体验，尚未在用户浏览器复现悬挂。 |
| 2 | 实例页面刷新 | `static/fleet.js` 每两秒 `loadFleet()`，无进行中标志／响应代次校验；非实例页面也生成实例卡片，整块替换后又更新其中的 live 区域。 | 防重入、丢弃旧响应；当前实例摘要与全实例详情分开获取；按可见页面刷新，保留 DOM 做增量更新。能减少请求、字符串拼装和 DOM 工作；浏览器 CPU 收益尚未测量。 |
| 3 | 队列候选与领取查询 | 调度候选 SQL 169 次、返回 16,224 行、检查 226,817 行，平均每次约 1,342 行，累计 1.27 秒。代码强制 `ix_tasks_batch_seq`，索引没有 status，完成越多越需要越过历史记录。 | 优先设计批次＋状态＋序号的候选索引与查询分支，再验证 available_at、定向实例、公平性和 SKIP LOCKED。仅移除 FORCE INDEX 不足：补充 EXPLAIN 中优化器仍选择该索引。属于长期预防，目前不是秒级卡顿主因；EXPLAIN 的几十万 rows 是估计，不能当成实际扫描量。 |
| 4 | 近十分钟平均／折线图 | `statistics.output_history()` 每次按 session 读取明细，SQL 时间边界放宽一天，再在 Python 处理时区。89 次测试明细读取累计返回 **89,906 行**，最终图只有 30 个点。当前约 2.6 ms/次，但会随会话历史增长。 | 先对同一会话的图表做短缓存，随后使用规范 UTC 时间范围索引或按分钟持久汇总；保留重建和幂等校验。不能直接按带不同时区的 ISO 字符串收紧范围，否则会漏计。降低查询量不代表下载速度同幅增加。 |
| 5 | 合并、校验与删除 | 大文件后处理更长，且磁盘写入有突发，iowait 最高 13.65%。 | 先细分记录合并／ffprobe／复制／清理耗时与字节，再按磁盘压力给本地后处理设置独立有界队列。单独限制合并可能增加临时磁盘占用，须同时检查空间和任务租约。保留画质和校验，先验证再设数值。 |
| 6 | 进度、心跳和速度展示 | 等待请求阶段通常没有新字节事件；接口快不等于进度内容每秒变化。当前进度更新时间间隔可以超过十秒。 | 分开显示任务心跳、最后字节变化、阶段耗时和已完成成品速度；阶段等待时不沿用旧瞬时速度。任何卡死判断同时看租约、心跳、进度与阶段，不能用一个统一短超时终止所有大文件。 |
| 7 | Redis 回退可观测性 | `ProgressCache._call()` 异常被吞掉，5 秒退避后继续；原始 Redis 命中率也看不到 attempt／租约／旧时间拒绝。当前没有故障证据。 | 添加限频告警、失败／退避／回退计数、按原因的缓存拒绝指标；有必要时批量读取多任务进度。保留 MySQL 所有权及租约检查，不能让缓存决定执行权限。 |
| 8 | SQL 与进程心跳开销 | COMMIT 约 44/s；有大量轻量实例和资源状态读取。整体平均延时低，当前收益小于前面几项。 | 对只读汇总和非权威展示复用短快照，减少重复连接与重复查询；不能缓存或移除领取、停止、租约、冷却的最终事务校验，也不建议降低 MySQL 持久性配置换取速度。 |
| 9 | 字幕汇总及闲置路径 | `subtitles.summary()` 按 action、实例两个归属字段的 OR 和 status 分组，状态接口及实例接口均可调用。当前仅少量字幕任务，未形成可观测热点。 | 字幕历史增长后再考虑维护分实例计数或短缓存，不能将当前数据库压力归因于字幕；确认补下载不会重复请求已成功副文件。 |
| 10 | 日志与故障分类 | 当前版本主要 warning 为部分 tv_samsung DRM 格式跳过，仍有大量成功任务。日志有上限，旧日志里仍存在此前的 deadlock／crash 字样。 | warning 按类型计数并保留原文，错误展示按当前版本和时间筛选；不要因 DRM warning 全局删除 client，也不要把旧异常当新故障。 |
| 11 | 导入／上传的磁盘预算 | `disk_uploads.py` 流式 write 可逐块强制检查预算；文件越大、分块越小，重复扫描成本可能增长。当前没有导入负载，未实测为热点。 | 有活跃导入时测每块检查次数和预算耗时；考虑按已写字节＋时间节流，保持预留和磁盘不足保护。不要通过关闭预算检查优化。 |
| 12 | OSS 上传 | 当前没走 OSS；代码的 resumable upload 固定 2 线程、8 MiB part，不能用当前下载结果解释 OSS 速度。 | 切换到真实 OSS 工作负载后，独立测上传阶段、重试、CRC、分片并发和本地写入；避免上传过量竞争下载磁盘与带宽。本轮未向 OSS 写测试对象。 |

## 下载耗时：区分限频等待与大文件

初始最近半小时 140 个结束任务中，130 成功、10 失败；这个窗口横跨优化上线前后，不能用作当前 r2 的失败率。阶段中位数分别为：解析 7.67 秒、请求休眠 30.06 秒、等待传输名额 0.042 秒、实际下载 9.09 秒、处理 1.5 秒。各阶段统计的样本数不同，不能把中位数相加当作精确的平均任务耗时。

最近 200 份测试成品按体积分类：

| 成品大小 | 样本 | 实际下载中位 | 后处理中位 |
| --- | ---: | ---: | ---: |
| 小于 100 MiB | 41 | 2.09 秒 | 0.5 秒 |
| 100 MiB—1 GiB | 130 | 11.70 秒 | 1.6 秒 |
| 超过 1 GiB | 29 | 83.40 秒 | 9.7 秒 |

大文件样本最大约 5.56 GiB，部分下载超过八分钟。文件大小、上游速率和格式都不同，这不能单独证明某个大文件一定正常或一定限速，但足以说明不能统一用一两分钟认定卡死。

当前传输名额等待很短，暂不支持“增加并发就能解决卡顿”的建议。配置分片并发为 8 也不等于实际每任务发出 8 个连接：现有连接预算会进一步收紧。本轮没有扩大实际请求数。

## Cookie 保护及请求边界

- 当前版本过滤后的 83 次准入最小启动间隔 **10.189 秒**、平均 **10.393 秒**，没有新的 `attempt_released`、`worker_crash`、`heartbeat_error`、`lease_abandoned` 事件。
- 76 次结束中只有一次失败，发生在异常 Cookie 冷却到期后的自然任务，时间 **15:22:04**，仍为 transfer 403。它没有被自动切换到其他账号重试。
- 已按设计把该 Cookie 再冷却 **30 分钟，至约 15:52:04**；其他 11 个会话继续，池没有整体 halt。本轮没有人为触发探测。
- 当前是固定间隔 `manual` 模式。配置中的每小时 80、每天 1,200 预算仅在 `adaptive` 路径执行，页面也标明“渐进模式生效”；这些数值**不能当作当前模式已经执行的累计硬限制**。如果要让账号池在固定间隔下同样受累计预算约束，需要专门设计持久计数和展示，不宜直接切换模式作为这次诊断的附带动作。
- 日志准入事件没有显式 source_address，当前策略为 direct。不能把 Cookie 数量等同于独立公网出口数量；本轮没有外联验证每个 Cookie 的出口。
- 即使上述保护正常工作，也不能保证平台不触发风控。优化目标是减少本地浪费、准确识别异常、维持退避，不能把取消休眠、缩短冷却或跨账号补打 403 当作提速措施。

## 建议执行批次

第一批：只读接口超时／防重入／旧响应丢弃、实例页面增量更新、图表短缓存、缓存回退指标。先解决页面稳定性，保持下载节奏。

第二批：在隔离 MySQL 的大队列样本验证新候选索引和查询，覆盖已完成历史很多、任务延迟、定向实例、停止和多进程竞争，再安排线上建索引窗口。

第三批：补齐后处理细分指标，实测独立背压；以成品完成速率、磁盘压力、临时空间、HTTP 延迟和 Cookie 异常数量共同验收。没有依据承诺固定百分比提速。
