# 美国服务器 yt-dlp 下载优化记录（2026-10-31）

## 结论与范围

在用户授权的一小时窗口（北京时间 11:44–12:44）内，对美国服务器 `88.210.37.181` 检查、测试、修改代码并部署。下载仅使用本机 yt-dlp，直接连接 YouTube / Google 视频 CDN，没有使用第三方视频解析服务器。

优化重点是有效登录、固定出口、限制视频解析启动节奏、遵守限流冷却，以及减少调度空转。没有破解验证码，也没有轮换 IP 继续请求已触发验证的站点。短期成功不能保证长期不会触发验证。

**任务保留了原有 `storage_mode=test`：真实下载、校验后删除临时视频，留下任务记录和统计。本文完成数量与字节数不代表服务器保存了这些视频。**

## 原因与证据

1. 接手时实例处于暂停状态，登录检查为未登录。旧 Cookie 文件的时间尚未过期，但 yt-dlp 明确提示服务端登录凭证失效或已轮换。文件过期时间不能替代实际登录检查。
2. 原服务的 yt-dlp 为 `2026.08.19`，本次升级至稳定版 `2026.10.26`，依赖锁定同步更新。
3. 原配置每个视频切换代理出口，节点跨多个地区。新的用户 Cookie 已在自有服务器直连下验证有效；登录检查和下载绑定同一 IPv6 路径，避免继续跨出口测试。
4. 原页面把匿名重试遇到的挑战也笼统展示为 Cookie / Cloudflare 问题，证据不足。本次按认证请求、匿名重试和具体错误来源区分；无法确认的错误保留不确定性，验证挑战仍暂停实例。
5. 队列有约 23.5 万个待处理任务。空闲准备进程在渠道繁忙时不断领取、释放下一个任务，增加数据库与日志负担。修复后会先退避再领取，等待期间不持有事务或任务租约。

## 直接下载与 IPv6 验证

服务器网卡有 16 个可用 IPv6，属于同一 `/64`；接口显示 `/56` 前缀不等于商家已分配整个 `/56`。这些地址不增加网卡带宽，也不能视作 16 份独立站点额度。

本次只固定使用 `2a06:f901:c001:100::fdb0:a5a2`。应用保留原 Docker 网络访问 MySQL，另接 IPv6 网络，通过 Docker SNAT 固定公网出口。登录预检和 yt-dlp 均设置源地址 `::`，不会静默退回 IPv4。实际路由、出口与 SNAT 规则均已检查。

| `MghIH4J4My8` | 隔离环境、无 Cookie，连通性基线 | 1080p、50,335,273 字节，端到端 9.46 秒 |

## 运行观察

生产队列于 12:03:06 恢复。第一阶段采用 4 路上限；为部署调度修复，12:14 左右停止领取新任务并等待大文件完成，12:20:54 恢复。12:24:17 将上限小幅提高至 6 路，其余节奏设置保持不变。

最终完成 **171 个视频、77,094,406,971 字节（77.09 GB）**；失败 9 个，其中 1 个私有视频、8 个账号限流。12:38 读取到明确账号限流后立即停止领取，已在处理的文件收尾，最终无活动下载。最后一次登录检查仍有效，但这不代表账号没有请求限制。

连续采样脚本此前有模块路径错误，12:28:23 修复；不把缺失时段当作完整连续监测。12:28:23–12:40:33 有效采样的媒体吞吐时间加权平均为 **343.29 Mbps（约 42.9 MB/s）**，包含限流后停止的低速时段。作为触发前参考，12:28:23–12:35:55 平均约 390.62 Mbps。采样显示了几百 Mbps 的实际传输能力，但没有证明该节奏可以长期持续。

**核心反例：固定 IPv6、有效 Cookie、单路解析、每 5 秒启动仍在本次窗口内触发账号限流。** 因而不能将这些措施称为已解决风控，也不能认定扩大至 6 路可以长期维持。源站没有返回 HTTP 429，而是在视频结果文本中明确提示账号被限流、最长可能一小时。

最终补充该文本错误识别：按账号限流处理，使用至少 3600 秒共享冷却和可重试属性，并增加独立页面风险说明。内部复用调度器的 429 冷却类别，不宣称实际观察到了 HTTP 429。此次已失败的 8 个记录保留，冷却结束后再人工重试。实例保持暂停，不自动切换 IP 或账号继续测试。

私有视频为 `u6WJ-7Fdd0w`，源站明确返回私有视频。该类单视频权限错误不再污染整个渠道的健康判断；泛化的 `Video unavailable` 不会直接被判定为私有或删除。

队列空转修复的去重日志：第一版约 11 分钟有 3,437 次任务开始、3,373 次释放、66 次提供方启动；第二版初始约 3 分钟仅 20 次开始、3 次释放、17 次提供方启动。窗口长度与负载不同，但可确认大量无效领取已减少；领取次数不等于向 YouTube 请求次数。

原始状态为暂停，且 Cookie、下载器版本、网络及调度同时变化，所以没有可用于计算“提速几倍”的公平基线。4 路与 6 路使用不同视频、合并耗时不同，也不能仅以完成数量判定优劣。传输进度中的瞬时速度峰值不作为持续带宽承诺。

本次观察结束保持暂停，账号冷却至少至北京时间约 **13:44**；这只是最早复查时间，不代表到点一定恢复。恢复前核对同出口视频访问，再以降低后的节奏观察；本次一小时窗口无法验证恢复效果。

视频启动间隔由实例内多个进程共享，但它限制的是视频解析启动，不能控制一次解析中的每个 HTTP 请求。5 秒不是 YouTube 公布的安全额度。分片并发也只对适用的格式生效，工作进程数不等于连接数。

页面增加直连源地址、视频启动间隔、匿名重试开关、429 最短冷却设置及说明，保存后可回读。并发诊断显示启动等待及出口设置。源站 429 按共享范围冷却，`Retry-After` 更长时服从更长时间；恢复后沿用单路观察。验证码、机器人挑战和确定的登录失效继续暂停实例，保留任务等待处理。

临时文件预算与物理剩余空间分别判断，合并期间还可能需要副本。调度器会受解析、渠道、源站组、连接、磁盘和自动吞吐控制约束，因此上限 6 不代表一直会有 6 个视频处于传输阶段。私有、删除、地区、会员等明确视频限制按视频处理。

## 经验与资源建议

当前不建议购买更多 IP 或服务器来继续冲击同一账号。此次瓶颈已出现明确的账号限流，新增网卡地址不能解决它。优先冷却、降低视频启动频率，并把账号限流与 HTTP 限流分别观察。浏览器人工登录不由 yt-dlp 的源地址设置控制，必须另行确认实际出口。

后续应观察至少 24 小时的成功率、429 / 验证次数、媒体吞吐、已校验吞吐、磁盘峰值与流量消耗，再决定是否提高上限。持续运行没有观察到挑战，也不能证明未来不会发生。

应向商家确认持续带宽、月流量与超额计费：持续 300 Mbps 理论上约 3.24 TB/天。23.5 万个视频队列可能产生大量流量，不能用这次小样本准确外推总大小。当前测试模式会删除视频；若改为永久保存，需要另做存储容量与归档规划。
