# 服务器性能观察与优化优先级（2026-11-06 晚间）

目标：216.227.169.90，4 vCPU / 约 16 GiB，Docker + MySQL + Redis。结论适用于本轮实际下载负载，不能外推为最大承载量。

当前优先处理部署一致性、下载失败和页面刷新细节。没有观察到持续的 CPU、内存或数据库瓶颈，暂时没有证据支持增加机器配置、连接数或下载并发。后续扩大样本和本地修复见[失败原因追查](failure-investigation-20261106-evening.md)。

**1. 已处理的部署问题**

发现两个 MySQL 容器同时挂载同一个 `mysql_data` 数据卷，并同时具有 `mysql` 网络别名：一个容器健康，另一个持续启动失败，重启次数达到 12，日志反复出现 `Unable to lock ./ibdata1 error: 11`。这是两个数据库进程争用数据文件，不能与 SQL 行锁等待混为一谈。重复网络别名还会带来新连接解析到异常容器的风险；本轮没有据此断言此前每一次连接失败的原因。

经用户明确授权，仅停止异常容器 `youtube-downloader-local-mysql-1`（实际 ID 前缀 `46e34e10ebd3`）。健康容器名为 `46e34e10ebd3_youtube-downloader-local-mysql-1`，名字中的前缀容易造成误判，执行前已按实际容器 ID、健康状态、挂载逐项核对。后续核对创建时间，异常容器创建于 09:09，健康替换容器创建于 14:12；此前将异常容器称为“新容器”不准确，停止目标正确。

停止后验证：

- 健康 MySQL 保持运行，异常容器退出并保留。
- 应用内 `mysql` 只解析到健康容器 `172.19.0.3`，重新连接执行 `SELECT 1` 成功，含连接建立约 62 ms。
- 随后 3 次容器快照中，异常容器均保持退出状态。
- 未删除容器或数据卷，未重启应用，未修改数据库和调度参数。

**仍需安排维护：**统一 Compose 管理状态和容器命名，核实保留的数据卷后再清理异常容器。本轮的停止操作不代表部署状态已经整理完毕。不同容器的 Compose 版本标签不同，只能作为排查线索，不能据此确定冲突起因。

依赖健康、仅更新应用时，需在部署端的正确项目目录和 Docker 上下文中使用以下命令；后续确认服务器没有可用的 `docker compose` 子命令，部署记录来自 Windows。命令中的 Docker 客户端必须已连接目标服务器；本轮未执行构建或部署：

```sh
docker compose -f compose.local.yaml -p youtube-downloader-local up -d --build --no-deps app
```

**4. 接口、MySQL 与 Redis**

76 次已认证接口读取全部 HTTP 200。耗时为应用容器内部访问本机接口，包含服务处理，不包含公网链路和浏览器绘制。

|---|---:|---:|---:|
| `/api/jobs/workbench` | 94.9 ms | 120.3 ms | 168.9 ms |
| `/api/status` | 104.0 ms | 124.5 ms | 170.5 ms |
| `/api/overview` | 84.1 ms | 102.3 ms | 130.9 ms |
| `/api/instances` | 88.5 ms | 99.6 ms | 150.6 ms |

MySQL 8.4.13 的 InnoDB 缓冲池为 2 GiB，保持 `innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`。连接上限 151，结束快照为 49 个连接、2 个正在执行，历史峰值 52。空闲连接本身不等于正在消耗 CPU。

120 秒内的主要数据库数据：

- 查询计数增加 25,109，约 209 次/秒，包含审计读取。
- 13 次锁快照均为 0；事务快照基本为 0，一次为 1 且事务年龄为 0 秒。区间累计行锁等待仍增加 7 次、总计 115 ms，说明存在短暂竞争；并非“完全没有锁等待”。
- 缓冲池逻辑读取 310,082 次，物理读取 105 次，区间命中约 99.966%；无等待空闲缓存页。物理读取约 14 KB/s，数据库物理写入约 0.52 MB/s。
- COMMIT 3,680 次，平均约 1.75 ms；实例读取 1,768 次，平均约 0.20 ms；资源准入 `FOR UPDATE` 675 次，平均约 0.24 ms；可调度任务扫描 114 次，平均约 1.47 ms。
- 一类已结束任务列表 SQL 平均约 21.2 ms，6 次共检查 18,572 行、返回 36 行。可列入后续执行计划检查，当前总耗时仅约 0.127 秒，不宜直接为此增加索引。
- `Com_rollback` 增加 3,716，SQLAlchemy 关闭读取事务也会产生回滚，不能当成同等数量的业务失败。磁盘临时表增加 14 个，审计聚合查询也可能贡献，未据此归因应用。

任务表估算约 32.8 万行，数据约 280 MB、索引约 463 MB；预约表估算约 36.2 万行。行数来自 InnoDB 估计值。后续随数据量增长检查历史保留策略及分页执行计划，暂不直接删除记录或增加缓存池。

Redis 峰值使用约 1.26 MiB，上限 256 MiB，最多 25 个连接；180 秒内无淘汰、拒绝连接或阻塞客户端，命令增量 1,142。全局命中增量 674、未命中 18，约 97.4%；该比例不能代替“有效进度缓存命中率”。本轮没有触发故障回退试验。

**5. 下载产出、调度与失败**

最近半小时完成 97 个任务，91 个成功、6 个失败，样本成功率约 93.8%。成功成品字节共 72,317,939,385，约 72.32 GB；按 1,800 秒折算成品产出约 321.4 Mbps。成品完成时间与实际传输时间不同，这个数不能与网卡瞬时速率直接比较。

失败为 5 个格式不可用、1 个 HTTP 403。优先按已有任务日志核对格式选择条件、请求阶段和账号分布，再判断是否需要调整格式回退策略。DRM 格式跳过警告在成功任务中也出现，不能把每条警告都判成下载失败，或据此全局禁用客户端、降低画质。

12 个 Cookie 文件中，当前 1 个账号处于冷却，其他 11 个仍可调度。该账号已有多次 HTTP 403 记录，值得独立复核有效性和请求条件。403 只能确认该请求被拒绝，不能单凭状态码确定 Cloudflare、验证码或整台服务器 IP 被封。

配置中的 `worker_count=64` 和 `throughput_mode=auto` 不代表当前执行 64 路下载。实际为 Cookie 池独立调度，运行容量采样约 22，诊断中的有效渠道额度估算约 8；任务同时处于处理状态为 5–9 个，真正传输数量还会更少。提高普通 worker 配置不能自动解除账号、渠道或共享资源限制。

15 分钟有界日志读取了 114 个文件、约 12.1 MB，去重得到 884 条结构化事件，解析错误为 0。其中 84 次尝试启动，6 次因流水线背压释放，约 7.1%。与早先文档中的高频释放现象相比，本轮没有再次观察到相同规模的调度空转；两次负载不同，不能作为严格的优化前后对照。

实时 worker 应按心跳筛选，21:31 快照中，90 秒内心跳有效的记录为 8 个运行、4 个空闲；历史 worker 行不能全部计入当前并发。

**6. 页面性能与可改进细节**

本机无头 Chrome 经 SSH 隧道读取服务器工作台；桌面 1440×1050 观察 30 秒，再以 390×844 窄屏观察 20 秒。没有模拟手机 CPU，也没有评价用户实际公网访问延迟。页面脚本错误为 0，稳定观察期没有捕获超过 50 ms 的长任务，窄屏未发现页面整体横向溢出。

| 函数 | 桌面中位 / 最大 | 窄屏中位 / 最大 |
|---|---:|---:|
| `renderBatches` | 0.7 / 2.4 ms | 0.9 / 2.6 ms |
| `renderConcurrency` | 3.6 / 5.8 ms | 4.1 / 5.2 ms |
| `renderStatus` | 9.9 / 11.5 ms | 9.1 / 11.5 ms |

这些是函数同步执行耗时，不是完整帧耗时；`renderStatus` 会调用其他渲染函数，耗时不能再相加。结束时页面约 3,562 个 DOM 节点、桌面快照 7 张活动卡片，小样本未证明大量卡片场景的性能。

当前已经存在请求防重入、异常退避、隐藏标签页停止轮询、统计缓存等优化，不应重复当作缺失项。后续可做：

- **减少空闲启动状态轮询。** 本次请求计数含页面初始化，`/api/downloads/startup` 52 次、`/api/jobs/workbench` 48 次。首页即使没有启动流程，也会每秒查询启动状态；可在启动期间保持快刷新，稳定后降低启动状态请求频率，或与工作台响应合并。保持跨窗口启动状态可见。
- **统一刷新触发节拍。** 1 秒执行轮询与 2 秒常规刷新都会触发 `refreshExecution()`。已有防重入避免同时请求，但不保证先后完成的请求不重复；桌面 30 秒观察到 45 次卡片重绘。可统一定时入口或记录最近成功刷新时间，保留立即刷新、切换实例、旧响应丢弃和失败退避语义。
- **按变化更新 DOM。** `renderBatches()` 整体替换活动卡片，`renderConcurrency()` 遍历并重建所有并发面板，包括隐藏面板。可按任务 ID 更新变化字段，只绘制可见面板，并保留展开状态和焦点。当前实测开销小，属于后续体验改进。

**7. 建议执行顺序与验证方式**

| 优先级 | 工作 | 验证目标 |
|---|---|---|
| 高 | 维护时整理 Compose 和数据库容器归属 | 单一数据库进程使用数据卷，`mysql` 解析唯一，应用连接成功，重建后不再出现文件锁冲突 |
| 高 | 排查 5 个格式失败与重复 403 的账号 | 按原因统计失败和重试成本，确认格式策略及账号状态，避免把拒绝请求误判为硬件不足 |
| 中 | 合并 / 降低重复状态轮询、按变化渲染 | 对比同等卡片数下的请求量、重绘次数、长任务；启动 / 切换实例 / 失败恢复仍及时准确 |
| 中 | 完善等待原因与容量口径说明 | 区分配置值、池容量、渠道有效额度、运行数、真实传输数；等待倒计时可理解 |
| 观察 | 磁盘突发、历史数据增长和慢列表 | 长时间观察 IO 等待、队列年龄、查询执行计划；证据充分后再调参或增加索引 |

当前运行的是测试存储模式。本轮未覆盖大批导入、OSS 上传、浏览器下载渠道、字幕补下载的持续并发负载，也未做全天观测和容量压测；这些链路需要各自的真实业务样本。除停止已确认异常的 MySQL 容器外，本轮未实施上述后续优化。
