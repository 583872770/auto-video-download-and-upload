# HTTP 视频分块并行

yt-dlp 的普通 HTTP/HTTPS 媒体在文件大小已知、超过 10 MiB、源支持标准 Range 请求时，使用有界的并行下载。直播、字幕、大小未知的文件和外部下载器继续使用原生路径。HLS/DASH 等媒体保留 yt-dlp 原有分片下载。

在“系统设置 → 运行模式与并发上限 → 浏览器与分片预算”中设置“分片并发数”：

- `1`：普通 HTTP 视频保持顺序下载。
- `2` 或更高：符合条件的 HTTP 视频允许并行分块，每块 10 MiB。

每个任务的连接上限为：

```text
max(1, min(分片并发数, floor(本机连接预算 / 实例传输额度)))
```

分片并发数最大为 16。调度器在下载前预留相同数量的连接；手动和自动调节模式均受本机连接预算约束。内置渠道不再单独设置共享连接预算，自定义兼容渠道显式配置的共享连接上限仍然生效。音频和视频轨道按原有顺序下载，连接数不按轨道数量翻倍。

例如，实例传输额度 2、分片并发数 2、本机下载连接预算 4，可同时运行两个各有最多两个连接的视频任务。文件较小、源不支持并行或其他额度不足时，实际连接数会更少。

实现会先探测 Range 支持，再检查每块的 HTTP 206 状态、Content-Range、文件总大小、实际长度及源提供的 ETag/Last-Modified。数据按偏移顺序写入，最多缓存连接上限数量的块；缺块不会被跳过。瞬时错误按分片重试，429 等限制仍交由原有冷却逻辑处理。响应范围不兼容时，丢弃不可信的部分数据并回退顺序下载。

进度和速度在主线程汇总，速度采用跨块的约 5 秒窗口。取消会停止提交新块、关闭正在读取的响应并等待线程退出，只留下连续的部分文件用于恢复。重新分配任务时，继续遵守已有的重新下载策略。

日志中出现 `HTTP 分块并行：最多 2 个连接，每块 10 MiB` 表示已进入并行路径。并行可能改善请求等待造成的空闲，但实际收益取决于 CDN、线路和限流状态，不保证随连接数等比例提高。

## 传输异常的有限恢复

2026-11-09 核实账号池近 24 小时记录：3 个任务出现 `HTTP 分块下载失败：TransportError`，其中两个在第二次任务尝试成功；另一个后续因 HLS 空尾片失败。保留的堆栈明确显示 YouTube CDN 的 `Read timed out`，发生在分块内容读取阶段，未观察到 HTTP 403/429。其他两个成功任务的详细日志已按保留策略清理，不能仅凭统一报错推断其具体传输原因。

分块仍先按已有 `fragment_retries` 重试。传输异常耗尽重试后，等待所有并行连接退出，用同一 Cookie、同一出口和同一媒体 URL 降为单连接重建一次。此次降级属于同一次任务和账号准入，不重新解析视频、不重新申请启动次数。旧的部分文件会丢弃，避免资源变化时拼接不同时刻的数据。恢复成功不先报告下载失败，因此不会因该次已恢复异常触发任务重排或 Cookie 失败退避。

降级只有一次，不循环恢复；持续故障仍按原有任务重试上限处理。403/429、带 `Retry-After` 的 HTTP 限制及证书验证失败不会触发此单连接恢复。降级中遇到 HTTP 限制时，保留状态码和 `Retry-After` 交给原有冷却策略。

最终错误提示保留具体的超时、响应不完整或连接中断说明，详细原因先脱敏再显示，不再只显示 `TransportError` 类名。此机制减少瞬时网络问题造成的任务失败，不能保证持续异常的 CDN 或线路必然恢复。
