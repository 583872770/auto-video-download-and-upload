# 2026-11-11 洛杉矶 VPS 容量摸底

## 结论

已在现有 4 核、约 16GB VPS 上运行隔离模拟。20 实例、400 份虚构 Cookie 的准备和短阶段执行完成，但持续运行阶段触发宿主机 I/O 保护，未通过完整容量验收。不能据本轮结果承诺二十份真实下载实例能稳定运行。

本轮最明确的资源问题是磁盘 I/O。内存仍有数 GB 余量；测试停止并清理后，现有应用容器仍出现很高的磁盘读写。另采到全局任务领取锁与任务序号分配的行锁竞争，扩容时需要继续测量并缩短相应事务。

## 环境和隔离

- VPS：4 核，`MemTotal` 约 15.62 GiB，开始时可用内存约 8 GiB。
- 现有应用镜像：`youtube-downloader-app:database-budget-20261111-r1`。现有应用、MySQL、Redis 均保留原容器，结束时仍 healthy，容器 ID 未改变、重启次数为 0。
- 测试运行于新建 MySQL 8.4、Redis 7.4 和模拟协调器容器，内部网络不开放端口、不访问 YouTube。
- 测试协调器使用本机整理后的 `webapp/`、`Utils/` 源码，只读挂载；借用服务器现有镜像的 Python 和依赖，没有替换服务器正在运行的代码。
- 每次上传源码的逐文件 SHA256 保存在本机 `.runtime/capacity-20261111/server-*/source-manifest.json`。两轮间改进了测试脚本，后端业务源码没有修改。
- 测试资源总硬上限为 2.75 核、2688 MiB；实际占用低于硬上限。测试使用随机独立数据库、虚构 SID、独立状态和 SQL 池，没有读取业务 Cookie 或向业务库写测试数据。

## 第一轮：持续入队与调度

采用 1 → 5 → 10 → 20 个模拟实例，每实例 20 个 Cookie；每级运行 60 秒后结算在途任务，随后进入 20 实例、计划 600 秒的持续阶段。

每个节点配置最多 8 个任务，但本轮没有发布虚拟节点资源快照，真实代码读取到模拟容器的 1GB 内存，将每节点动态进程上限降为约 2。因此观测峰值为 40 个同时运行任务，不能标成 160 路测试。

| 已结束阶段 | 实例数 | 阶段时间（含结算） | 完成模拟任务 |
| --- | ---: | ---: | ---: |
| 1 | 1 | 67.28 秒 | 6 |
| 2 | 5 | 69.98 秒 | 30 |
| 3 | 10 | 71.68 秒 | 60 |
| 4 | 20 | 71.35 秒 | 120 |

上述已结束阶段合计记录 216 次完成；持续阶段还有执行，但因保护中止，没有生成最终完整统计及一致性报告，不计入完成总数，也不将其称为全部通过。

400 个独立虚构 Cookie 建立成功，20 次跨实例导入同一凭据的尝试全部被拒绝。各实例独立池的观测连接峰值为 22；这不包含真实数百个下载子进程的连接需求。

本轮还在每次尝试领取前逐条新增任务，会同时争抢任务编号和全局计数器，属于持续入队与调度的混合压力。现场锁采样明确见到：

- `schema_settings` 主键记录 `fleet_budget`：若干事务等候排他行锁。
- `sequence_counters` 主键记录 `task`：若干事务等候编号分配。

这是行锁竞争的证据，不能描述成整张表被锁住，也不能仅凭锁存在就判断所有调度已经阻塞。原始 `data_lock_waits` 行数统计的是阻塞关系，一个事务可以出现多行，不能把它当作等待事务数量。

协调器运行约 11 分半时，连续采样的整机 I/O PSI `full avg10` 超过 20%，触发保护。停止前记录到 20.69%、23.62%，对应 CPU 执行/steal 合计约 56.0%、50.3%，I/O wait 约 24.9%、26.5%。保护来源为 I/O，不能归因于 CPU 或内存耗尽。

125 个已保存宿主机样本中，可用内存最低约 7432 MiB；现有 `/health` 无失败，P95 约 13.3 ms，最大约 24.5 ms。这是轻量健康接口的结果，不能等同整个工作台页面都没有延迟。

## 第二轮：预填队列与虚拟节点预算

为区分持续逐条入队的影响，第二轮改为预填队列，使用真实容量计算函数生成每个虚拟 16GB 节点的运行快照，计划每实例最多模拟 8 个任务；并接入实际 DownloadStartGate，避免把大量本地门控返回混入成功领取耗时。

第二轮在准备阶段就再次触发整机 I/O 保护，尚未进入正式负载阶段。中止时 `full avg10=22.86%`、I/O wait 约 23.2%，可用内存约 9448 MiB。没有取得 160 个同时运行任务或预填队列对照结果，不能作性能前后对比。

后续工具增加了启动前 I/O 预检、初始化期间压力检查、SIGTERM 收尾、清理结果核对和外层 `launch-summary.json`，以便类似中止也有明确结果。两个 VPS 试验均保留原始中止数据，没有用后续冒烟成功覆盖。

## 清理后的只读 I/O 采样

确认所有本轮测试容器和测试网络已经删除后，再对原业务容器和磁盘采样 30 秒：

| 组件 | 磁盘读取 | 磁盘写入 |
| --- | ---: | ---: |
| 原业务应用容器 | 约 286.87 MiB/s | 约 325.49 MiB/s |
| 原 MySQL 容器 | 约 0 MiB/s | 约 1.15 MiB/s |
| 原 Redis 容器 | 约 0 MiB/s | 约 0 MiB/s |

以上是 cgroup 块设备字节计数的时间差，属于不同于公网带宽的磁盘吞吐。不能据这些值反推视频净下载速度，也不能把后续窗口与压测窗口相减推导压测的独立影响。

同一窗口磁盘累计读取约 286.87 MiB/s、写入约 327.58 MiB/s。测试资源全部停止后，I/O PSI `full avg10` 仍在约 11.81%～24.41% 间波动，说明当前业务运行时就存在较高磁盘压力。

随后 20 秒进程采样中，持续可见的写入主要出现在多个 `web_worker.py` 下载工作进程，单个观测约 5.55～18.02 MiB/s；Web 主进程约 0.07 MiB/s。两个采样窗口不同，不能直接求和比较。进程采样间隔为 2 秒，可能漏掉短命 ffmpeg 等子进程；父子进程 I/O 归属和缓冲写回也会影响观察，尚不能排除合并/归档，也不能把全部读写直接归到网络下载。

本轮没有做破坏性磁盘测速，不能确定磁盘性能异常来自应用读写方式、VPS 存储配额、宿主机竞争或其他底层原因。

## 工具验证与收尾

- 增加 `scripts/verify/verify_capacity.py`，说明见 [容量测试使用方法](capacity-testing.md)。
- 本机多个隔离小规模冒烟通过，包括独立池、Cookie 归属、实际准入/释放、进度缓存、已结算任务拒绝迟到更新，以及结束时没有遗留运行任务和许可。
- 最终脚本版本本机冒烟成功：2 个虚构 Cookie、2 个任务完成、迟到进度/续租/结算各拒绝 1 次，剩余 3 个任务保持排队，许可为 0；测试资源清理核对通过。
- Python 语法检查与 `git diff --check` 通过。没有修改应用业务代码，无需部署应用。
- VPS 最终仅剩原应用、原 MySQL、原 Redis，均 healthy、重启次数 0；没有本轮带 `frameflow.capacity` 标签的容器或网络。

## 后续优先级

1. 先按真实任务的解析、传输、合并、复制、归档阶段记录文件读写，结合进程生命周期取样，定位现有应用的高磁盘读写来源；再在不改动业务的前提下判断 VPS 存储能力。
2. 持续入队、普通队列调度、手动批量重试分别测试。缩短 `fleet_budget` 锁内工作，并评估批量编号/批量计数；不能直接删除保证原子准入的锁。
3. 按所有实例的主池、辅助通道和实际下载子进程一起核算 MySQL 连接预算。22 个模拟连接的结果不能验证真实多进程连接峰值。
4. 等整机 I/O 有稳定余量后再完成预填队列对照、20 实例持续运行和更长时间验证。

此外，本轮只验证实例归属，所有虚拟实例位于同一物理 VPS。当前 Cookie 绑定表保存凭据摘要与实例作用域，没有保存固定服务器身份；实例身份冲突检查也不能替代永久的宿主机归属。用户要求的“只能在固定服务器下载”仍需单独核实和补齐，不能凭本次同机模拟声称跨服务器约束已验证。
