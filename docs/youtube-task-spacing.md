# YouTube 任务间隔

设置页将原来的“YouTube 视频启动最小间隔”改名为“两次任务启动最小间隔”，配置键仍为 `youtube_start_interval`，已有配置继续使用。新增“任务结束后休息时间”，配置键为 `youtube_task_rest_interval`，默认 0 秒（关闭），可设置 0–3600 秒。

两次任务启动最小间隔从上次启动时计时；任务结束后休息时间从上次视频任务执行结束时计时。二者与预算、冷却、并发等限制同时生效，取更晚的可启动时间，不将两项间隔直接相加。若启动间隔 100 秒、结束后休息 30 秒：任务耗时 20 秒，下次最早在启动后第 100 秒；耗时 150 秒，下次最早在第 180 秒。账号池还保留现有的启动抖动及预热、恢复保护。

账号池按核心 Cookie 会话分别计算，重复导出共享记录；一个账号休息不阻止其他账号下载。非账号池模式按当前实例计算，固定和渐进调速模式都支持。已开始的并发任务继续执行；结束后休息约束后续启动，不会取消在途任务，也不会把已配置的多路并发改成串行。

已经取得源站请求许可的任务，无论成功、内容错误还是传输失败，正常退出执行时均记录结束时间。未开始源站请求的本地资源等待不计入。视频执行结束包含合并及该执行流程的 OSS 交付，测试模式最后的工作目录清理不计入；后台字幕任务受账号现有间隔约束，但不会重新启动视频任务的休息计时。崩溃、强制终止或丢失租约时无法保证取得准确的结束时间。

结束时间使用现有数据库调度状态保存，没有新增表和后台轮询。保存设置后，后续领取的任务按新值判断；已有任务保留执行时的配置。休息截止时间由结束时间和新任务配置计算，因此后续任务可以使用提高、降低或关闭后的休息值。滚动预算、源站错误冷却和已预留的启动间隔不会被清空。

工作台 Cookie 卡片显示独立的“任务结束后休息中”状态和倒计时；仍受更长的启动间隔约束时同时展示该原因。设置页运行摘要显示已保存的两项间隔，使用同一个“保存设置”入口。
