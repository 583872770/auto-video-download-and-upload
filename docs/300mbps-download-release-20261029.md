# 300 Mbps 下载调度：部署与业务实测

日期：2026-10-29。本文记录前期[吞吐研究](300mbps-throughput-study-20261029.md)之后的实际实现、部署和正常任务观测。**新版已经上线，但尚未达到持续 300 Mbps 的目标。**

## 已上线的改动

- Bergung / Cobalt 的共享解析槽位现在复用专用事件循环、Playwright/CDP 连接及页面。同站点、API、画质和验证设置不变时省去重复设置页；每次仍重进主页，并核对 API 请求中的视频 URL，避免使用上次响应。失败、取消、配置或出口变化、空闲回收时关闭或重建。此优化不代表 yt5s、yt1d 等其他解析器也已采用同样的页面复用。
- 解析完成后、等待下载许可前就发布实际媒体上游和阻塞资源。准入每次重试都读取最新动态额度，避免已有地址仍按旧额度等待到超时、再次解析。
- 吞吐控制器分别识别全局传输需求、上游需求及共享配额限制；全局到顶后仍可调整上游额度。试增没有真正增加活动传输时，不将供给中断判为测速失败。解析阶段 CPU 压力上升时优先收敛浏览器；持续 CPU 压力、低内存及 I/O 压力仍会收敛传输。
- 渠道、媒体上游、API 后台、共享配额及本机连接预算仍是重叠约束。未经证实独立的媒体后台继续共用 `unverified-media`；Googlevideo 直链归入 `youtube-origin`。没有按域名数量推定独立带宽。

完整流程及跨实例许可机制见[下载调度文档](download-scheduler.md)。本轮没有启用普通文件 Range 并行或跨渠道拼接，也没有改变代理出口和画质设置。

## 15 分钟正常任务结果

先观察预热 240 秒，再于北京时间 **20:37:32–20:52:32** 连续观察约 900.14 秒，每 5 秒采样。不添加公共测速流量，不创建生产测试任务，不切换出口。以下为整个窗口的平均值，而非滚动面板峰值。

| 指标 | 结果 | 口径 |
| --- | --- | --- |
| 实际媒体接收 | **119.83 Mbps，约 14.98 MB/s** | 各渠道媒体进度字节计数的增量，可能包含重试下载 |
| 完成并校验的文件吞吐 | **102.95 Mbps，约 12.87 MB/s** | 窗口内成功任务文件大小合计 11,583,406,458 字节 / 窗口时长 |
| 下载容器网卡接收 | 133.54 Mbps | 包含网页、协议等其他接收；5 秒区间峰值 236.42 Mbps |
| 物理 `eno1` 接收 | 136.83 Mbps | 单独计数物理接口，避免 bridge/veth 叠加；包含其他主机业务 |
| 任务终态 | 成功 40，失败 2 | 失败分类为验证 1、其他 1；不等于渠道尝试失败数 |
| 渠道尝试结束计数 | 成功 40，失败 17 | 结束事件的失败占比约 29.8%；包含回退，且不是窗口内新开始尝试的完整队列失败率 |

| 主机 CPU 平均 | 75.8% | 4 核全机口径，含其他应用 |
| 本服务 cgroup CPU | 全机容量的 61.19% | 同一窗口 CPU 累计使用时间差分，包含已退出子进程 |
| 高 CPU 采样比例 | 28.7% | 控制器 CPU 读数不低于 90% 的采样比例 |

| 磁盘可用空间最低 | 30.00 GiB | 当前测试模式下观测值 |

成功任务来自 downmp3 24 项、yt5s 10 项、yt1d 5 项、Cobalt girlskissing 1 项。其余多个 Cobalt 入口有失败或没有产出，不能宣称添加这些域名已经叠加出多份独立带宽。媒体阶段的 429/503 专用计数本窗口为 0，不代表所有网页/API 请求都没有限流。

全局传输额度在 7–9 之间自适应，浏览器在 1–3 之间调整。181 个采样中约 58% 没有就绪任务；其他时刻也存在等待本机上游额度、全局传输额度的情况，说明解析供给和下载准入需要分别处理，不能只增加某一个并发参数。

媒体接收与完成字节包含不同时间边界：文件可能跨窗口下载/完成，回退可能改变编码，也可能重试。二者差额不能直接当成浪费。此前研究窗口和本次窗口的任务、渠道及运行状态不完全一致，不能据此报告严格的提速百分比。

## 剩余瓶颈与下一步优先级

1. **首先增加健康渠道的稳定产出。** 当前成功解析只有约 3.2 次/分钟，供给频繁断档；多个 Cobalt 入口未形成稳定产出。优先比较健康渠道在实际视频、同画质和同出口下的解析延迟、成功率、媒体速度及总吞吐增量。继续保留故障入口退避和少量恢复探测，避免不稳定入口长期占浏览器。
2. **对其他高产渠道复用解析运行时，再决定是否增加浏览器。** 此次持久页面优化覆盖 Bergung / Cobalt，而本窗口大部分成品来自其他解析器。对这些路径先测量浏览器准备、站点转换和验证耗时，复用能省去的部分；网站后台转换等待并不会因复用而消失。当前 CPU 已有明显压力，不宜直接大幅增加浏览器或在同机复制容器。
3. **对真实媒体路径比较出口和独立上游。** 在固定总并发下试验新增路径的总吞吐增量；域名、节点名称或单次连通结果不证明资源独立。出口绑定及签名要求未知时保持原出口。公共文件测速不能代替实际媒体效果。
4. **数据库池暂时保持。** 当前总连接远低于 500，没有新增连接失败，下载和等待不应持有数据库事务。`VIDEO_DB_POOL_SIZE` / `VIDEO_DB_MAX_OVERFLOW` 是每进程设置，放大它们会增加多实例的理论连接需求，并不直接增加下载带宽。
5. **磁盘及硬件按持续证据决定。** 另一个 45 秒诊断窗口 SSD 忙碌约 22.75%、写等待约 6.59 ms，尚不能证明 SSD 持续饱和；本窗口有 I/O 压力，仍需监控。只有健康上游、出口和供给充足后仍长期 CPU 饱和，才据此评估更强 CPU 或独立解析资源。正式留存时必须保证上传/清理速度跟上，30 GiB 可用空间无法长期承接 37.5 MB/s 新数据。

这些指标存在共同变化，不能把“解析、CPU、上游、磁盘”各自折算成可相加的因果百分比。下一轮应固定画质、任务集合、出口和其他负载，交替进行至少 15–30 分钟的业务观测，同时比较完成吞吐、媒体吞吐、失败率和资源压力。

## 验证与最终健康

- Windows 本地完整测试：534 项，成功，跳过 29 项。
- Linux 候选完整测试：536 项，成功，跳过 19 项。此后仅调整供给中断判断及对应测试，Windows / Linux 各运行调度与吞吐回归 42 项并通过；没有将最终增量描述成又一次完整测试。
- 四组界面验证通过：自动渠道、实例管理、任务状态、设置保存。编译及差异空白检查通过。
- 需要独立测试数据库的 MySQL 契约测试未运行，没有为了测试改写生产数据库。
- 北京时间 20:53:17 复核：容器 `healthy`，重启 0，OOM 0；主实例持续运行，10 个运行任务的租约均有效；数据库 31/500 连接，无实例错误，磁盘可用约 30.37 GiB，吞吐控制器持续更新。
